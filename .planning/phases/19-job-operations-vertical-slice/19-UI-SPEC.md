## Visual Focal Points

- **Job list:** the status badge column is the visual anchor — it is the only scannable signal that differentiates rows at a glance in an otherwise text-dense table; the "New Job" button is the only accent-colored call-to-action, drawing the eye to the single entry action (row "View"/resource links are also accent per the Color contract, but they read as inline navigation, not competing calls-to-action).
- **Job detail:** the header row (Job type + short ID, 20px/600 heading, status badge, and the D-14 honest cancellation/outcome label when present) is the visual anchor — it is the first thing read on the page and is what every other panel (progress, logs, events, resources, result) elaborates on.

### Mutation error copy (typed 4xx bodies)

`GET`/read failures use the existing `ErrorState` (`fetchApi` extracts `detail` only when it is a string). Job **mutation** routes (`POST /api/v1/jobs`, `POST /api/v1/jobs/{id}/cancel`) return a structured JSON body `{"detail": {"code": "...", ...}}` (`HTTPException(detail={"code": code, **detail})` at `api/routes/jobs.py:63`, wrapped by FastAPI's default handler; no custom handler unwraps it) — `detail` is an **object**, not a string, so `fetchApi`'s existing string-only extraction falls back to a bare `HTTP {status}`, which is not acceptable copy. The mutating client must read `body.detail.code` and map it through this closed table; an unmapped code renders `Operation failed ({code}). Try again; if it persists, check the API logs.` rather than crashing:

| `code` | Copy |
|--------|------|
| `missing_idempotency_key` | `Missing idempotency key — this is a console bug, not an operator error. Reload the page and try again.` |
| `invalid_idempotency_key` | `Invalid idempotency key format — this is a console bug, not an operator error. Reload the page and try again.` |
| `unknown_job_type` | `"{job_type}" is not a registered Job type.` |
| `invalid_job_payload` | `This submission was rejected: {reason if provided, else "invalid payload"}.` |
| `idempotency_key_conflict` | `Idempotency key reused with a different payload — this is a console bug, not an operator error. Reload the page and try again.` (409 fires only when the same key is reused with a **different** request fingerprint — `job_mutations.py:192`. **Do NOT** navigate to `original_job_id`; the form stays open with the operator's input intact. The `Already submitted — opening existing Job` copy + navigation belongs **only** to the true replay path: `200` + `Idempotency-Replayed: true`.) |
| `invalid_cancellation_reason` | `Cancellation reason must be 500 characters or fewer.` |
| `job_not_found` | `Job {job_id} was not found.` |
| `job_not_cancellable` | `This Job is already {status} and cannot be cancelled.` |
| `mutations_disabled` (ORCH-07 403, exact string is Claude's discretion — recorded here as the working name) | `Mutations disabled on this deployment` (same string as the inline reason, for consistency) |

## Component & Interaction Notes

These extend the template's required tables with testable invariants the checker/planner/executor need; they are not optional flavor text.

### Cancel trigger button (Job detail) — styling
The `Cancel Job…` button that opens the confirmation dialog is **neutral/secondary styling**, mirroring the existing `FetchMeta` refresh button treatment exactly. Use the identical class string with only the vertical padding changed to the 8-point scale: `rounded border border-zinc-700 px-2 py-1 text-zinc-300 hover:bg-zinc-800 disabled:cursor-not-allowed disabled:opacity-50` (source: `FetchMeta.tsx:28`, `border-zinc-700` border, no fill, `text-zinc-300` text, `hover:bg-zinc-800`, `py-0.5` swapped for `py-1`). This is not accent (`sky-400`, reserved per the Color contract) and not destructive-filled (`red-900`, reserved for the dialog's confirm button only per the Color contract). This keeps the destructive color signal exclusively on the point of no return (the dialog's confirm action), not on the button that merely opens a confirmation. Padding is pinned to exactly `px-2 py-1` (8px horizontal / 4px vertical, both on the 8-point scale) — the 2px badge/chip exception does not extend to this button. The `disabled:` classes above already cover the disabled + inline-reason state (`Mutations disabled on this deployment`) when `mutations_enabled` is false (D-21); hidden entirely on terminal Jobs (see Copywriting Contract).

### Cancel confirmation dialog — implementation constraint
No dialog/modal component exists anywhere in the console today. **Do not use the native `<dialog>` element's `showModal()`/`close()`** — verified against the installed `jsdom@29.1.1`: `HTMLDialogElement`'s jsdom implementation is an empty subclass of `HTMLElement` with no `showModal`/`close` behavior, so component tests calling it would need a manual stub. Build the confirmation as a plain React-state-controlled overlay (`role="dialog"`, `aria-modal="true"`, a `zinc-950/80` backdrop, `zinc-900` panel with `zinc-800` border) instead — zero new dependencies, testable with Testing Library without stubbing browser APIs.

### D-14 honest cancellation/outcome label — case table
The label renders **only** when at least one of `cancellation_requested_at` is non-null, `cancellation_cause` is non-null, or `failure_reason === "cancellation_timeout"`. Otherwise the Job detail shows its normal status/failure_message and no cancellation label. This scopes the function to cancellation-related states only — plain crash failures (`worker_lost`, `lease_expired`) and plain `handler_error` failures render through JOBUI-02's generic failure_reason/failure_message/outcome_uncertain display, not this function.

| status | cancellation_cause | resources[0].status (if any) | Label |
|--------|--------------------|-------------------------------|-------|
| `cancelled` | `operator_request` | (no resource exists) | `Cancelled before start — never executed` |
| `cancelled` | `operator_request` | `succeeded` | `Cancelled — linked run had already completed (SUCCEEDED)` |
| `cancelled` | `operator_request` | `failed` | `Cancelled — linked run had already completed (FAILED)` |
| `cancelled` | `operator_request` | `running`/`queued` (resource exists but not yet terminal — should not occur under D-12/D-13 but rendered defensively) | `Cancelled — linked resource is still in progress` |
| `cancelled` | `dependency_failed` | n/a | `Cancelled automatically — a dependency failed; this Job never ran` |
| `cancelled` | `dependency_cancelled` | n/a | `Cancelled automatically — a dependency was cancelled; this Job never ran` |
| `failed` | (failure_reason = `cancellation_timeout`) | (no resource) | `Cancellation timed out — outcome uncertain; no linked resource found yet` |
| `failed` | (failure_reason = `cancellation_timeout`) | `running` | `Cancellation timed out — outcome uncertain; run still RUNNING` |
| `failed` | (failure_reason = `cancellation_timeout`) | `succeeded` | `Cancellation timed out — outcome uncertain, but linked run shows SUCCEEDED` |
| `failed` | (failure_reason = `cancellation_timeout`) | `failed` | `Cancellation timed out — outcome uncertain, but linked run shows FAILED` |
| `running` | (none) | `cancellation_requested_at` set, `cancellation_acknowledged_at` null | `Cancellation requested — waiting for the next step boundary` |

**Explicitly unreachable, not tested as positive cases (structurally prevented, per Phase 17/18 code):**
- `status=queued` with `cancellation_requested_at` set — queued cancel is atomic (transitions straight to `cancelled` in the same DB operation, `17-06` D-07); a `queued` row with a cancellation timestamp should never be observed.
- `status=succeeded` with `cancellation_requested_at` set — a running cancel never lands `SUCCEEDED` (D-12); the post-call checkpoint lands `CANCELLED` instead when acknowledged after a successful call. Also structurally prevented: cancelling an already-terminal (`succeeded`) Job is rejected with `job_not_cancellable` (409) before any write occurs.

### Polling contract (JOBUI-05)
- Job **list**: polls while **any visible row** has a non-terminal status (`queued`/`running`); interval **5s**; stops entirely when every visible row is terminal.
- Job **detail**: polls while the Job's own status is non-terminal; interval **3s**; stops the instant it observes a terminal status.
- Both pause while `document.hidden` is true (tab not visible) and resume on visibility regain, per CONTEXT's "pause-when-tab-hidden" discretion note.
- Background polling ticks must **not** flip `FetchMeta`'s `loading`/`"Refreshing…"` state — that would flicker the Refresh button every 3–5s. Use a separate, small "Auto-refreshing every {N}s" / "Auto-refresh stopped — Job finished" indicator (see Copywriting Contract) next to `FetchMeta`, driven by its own state, not `FetchMeta`'s `loading` prop.

### `resources[]` and `result_summary` rendering (JOBUI-02)
- `resources[]` renders as a list of `{kind}: {id}` rows; a row whose `kind === "strategy_run"` links to `/runs/{id}` (accent color, per Color contract); any other/unrecognized `kind` renders as plain `zinc-300` text with no link (see Copywriting Contract fallback row) — this is what keeps the component job-type-agnostic and lets a test-only Job type with an unrecognized `resources[].kind` pass SC6 unchanged.
- Empty `resources[]` and absent `result_summary` render the copy defined in the Copywriting Contract table above; branch that copy on Job status (terminal vs non-terminal) and on `resources.length`, never on `job_type` (see Lookup-map discipline below).
- `result_summary` renders generically as a `dl`/key-value list via `Object.entries()`, with nested objects/arrays passed through `JSON.stringify()` — same pattern as `StrategyOverviewPanel`'s open-ended config rendering (14-01 precedent). No key is ever special-cased in this generic view (`run_id` inside `result_summary` is plain data here; the authoritative navigable link is `resources[]` only, per D-06).
- Job IDs render as the full UUID in `font-mono text-xs` with `break-all` (matches `RunHeaderPanel`'s `run_id` treatment). Timestamps render as the raw ISO string returned by the API, unformatted — same precedent as `started_at`/`completed_at` elsewhere in the console; do not introduce a new timestamp-formatting convention for Job UI alone.
- Progress bar: when `progress.percent === null`, render an indeterminate (animated, non-numeric) bar with the `progress.step` text beside it (e.g. `resolving strategy`); when `percent` is a number, render a determinate bar at that width. Never interpolate or fabricate a percentage.

### Logs and Events panels — empty-state reachability (verified against `jobs/runner.py`, `jobs/context.py`, `jobs/dependencies.py`)
- **Logs:** rows in `job_logs` are written only via `JobContext.log()`, called from inside a handler (`jobs/context.py`). A QUEUED Job (not yet claimed by a worker) has zero log lines by construction — this is the common reachable empty state, not an edge case. A terminal Job can also have zero log lines if it failed before the handler logged anything (e.g. `config_invalid` at pre-dispatch validation, or `worker_lost`/`lease_expired` before the handler ran).
- **Events:** every Job receives a `SUBMITTED` JobEvent in the same transaction that creates the row (`jobs/dependencies.py`, `_create_job` path) — so a Job with zero events should never be observed in practice. Treat the "no events" empty state as defensive rendering only (same posture as the D-14 unreachable-cases note above), not as a normal state a developer should expect to see in manual testing.

### Lookup-map discipline (D-17)
Exactly two lookup maps exist in the console, each in one module: (1) `job_type → form component` (used only by `/jobs/new`), and (2) `resources[].kind → route` (used only by the generic resource-link renderer above). List/detail/log/event components must not import map (1) and must contain zero `job_type` conditionals — this is what SC6's "render a test-only Job type through list and detail with zero UI changes" component test verifies. This includes the empty-state copy above: it branches on Job `status` and `resources.length`, never on `job_type`.
