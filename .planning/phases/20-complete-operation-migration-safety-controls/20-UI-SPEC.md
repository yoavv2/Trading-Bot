# Phase 20 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope Note

ORCH-01, ORCH-02, and ORCH-08 (bypass retirement, boundary tests, script/Makefile/worker-command deletion) are backend/tooling-only — they add no browser UI. ## Visual Focal Points

- **`/jobs/new` type picker:** unchanged structurally — the focal point is the job-type list itself; each item's `job_type` link is the existing accent-colored (`text-sky-400`) navigational element from Phase 19 (see Color contract note above; no contradiction — it is accent, and it is already covered by the existing reservation).
- **Job detail (FAILED/CANCELLED Jobs):** the `Retry` button is the second focal point after the status badge — it must visually read as the primary next action for a terminal, non-succeeded Job, using the same accent weight as `New Job`.
- **`/controls`:** each control's current-state display (reusing `KillSwitchPanel` and the shared `StrategyStatusBadge`, per the corrections above) is the focal point per section, with its trigger button positioned immediately beside it via the `renderAction`/inline-slot pattern, so state and the action that changes it are always read together.
- **`KillSwitchBanner` (armed state, new):** the slim informational bar (see Component & Interaction Notes) is deliberately low-key — it must never compete visually with the alarming full-width red banner shown when tripped.

### Retry rejection copy stays link-free (mutation error table)

The mutating client's error path (`submitJob`/`cancelJob`/`retryJob`, all in `console/src/lib/api.ts`) returns `result.message: string` on failure — a plain string cannot embed a working React `<Link>`. So every entry below is **plain text only**; the moment a rejection is observed, the confirm dialog also triggers a Job-detail refetch (mirroring `CancelJobDialog`'s existing `onCancelled`/`onChanged` callback), and any clickable link (the retry lineage link, the reconciliation deep-link) renders **only** from the freshly-refetched `JobDetail` fields (`retried_as_job_id`, `retry_blocked`) in the disabled-trigger area described above — never inside the transient error message itself.

| `code` | Copy (plain text, dialog body) |
|--------|------|
| `job_not_cancellable_running` | `Not cancellable once running` (same string as the disabled-trigger reason — if a stale view sends the request anyway, the 409 surfaces identically, per CONTEXT D-03a) |
| `reconciliation_required` | `Retry blocked — the original Job's outcome is uncertain. Run reconciliation first, then retry.` |
| `retry_exists` (working name — exact string is Claude's discretion per CONTEXT) | `This Job already has a retry.` |
| `job_not_retryable` (working name — retry of a non-terminal or SUCCEEDED Job) | `This Job cannot be retried — retry is only available for FAILED or CANCELLED Jobs.` |
| `invalid_retry_payload` (working name — D-18 re-validation failure) | `This Job can no longer be retried: {reason if provided, else "the original payload is no longer valid"}.` |

Unmapped codes fall back to the existing Phase 19 generic copy: `Operation failed ({code}). Try again; if it persists, check the API logs.`

## Component & Interaction Notes

These extend the template's required tables with testable invariants; they are not optional flavor text. All notes from `19-UI-SPEC.md`'s "Component & Interaction Notes" section (Cancel trigger styling, D-14 cancellation label table, polling contract, `resources[]`/`result_summary` rendering, empty-state reachability, lookup-map discipline) remain in force unchanged. Only new/extended notes are listed below.

### Verified against the SC6/D-17 boundary test (`console/src/lib/consoleBoundaries.test.ts`)
Grepped directly. The test enforces exactly four things: (1) no `fetch(` outside `lib/api.ts`; (2) no Job-UI-scope file (everything under `components/jobs/` except `components/jobs/new/`, plus `app/jobs/page.tsx` and `app/jobs/[jobId]/`) imports `jobTypeForms`; (3) no Job-UI-scope file contains the literal string `"backtest"`; (4) no Job-UI-scope file branches on `job_type` equality or `switch`es on it. **`JobHeaderPanel.tsx` is inside this scope** (it is one of the `EXPECTED_JOB_UI_FILES`). The retry-blocked deep-link therefore must not hardcode any job-type string (e.g. `"reconciliation"`) inside `JobHeaderPanel` or any other Job-UI-scope file — see the API contract dependency below, which moves that value server-side. This also means the console's confirmation of "job-type-agnostic" is a real, already-running automated check, not just a design intent — Phase 20's new Job-UI-scope code must keep passing it unmodified (no test edit is authorized to loosen these four assertions).

### API contract dependencies this UI-SPEC introduces (planner must schedule these; not optional)
- **`JobDetail` gains `payload: Record<string, unknown>`** (currently absent from `services/job_reads.py` `get_job_detail` / `console/src/components/jobs/types.ts`). Required to render the Retry confirmation dialog's payload preview.
- **`JobDetail` gains a server-derived `retry_blocked: { code: string; required_job_type: string; strategy_id: string | null } | null` field.** This is the mechanism that resolves the D-19 gating problem without any client-side `job_type` literal: `required_job_type` and `strategy_id` are read straight off this field to build the `Run reconciliation` deep-link (`/jobs/new?type=${retry_blocked.required_job_type}&strategy_id=${retry_blocked.strategy_id}`) — fully generic, computed server-side, satisfying the boundary test above by construction (no job-type string ever appears as a literal in `JobHeaderPanel.tsx`'s source). This field is `null` for every Job the D-19 rule does not currently block. **`JobHeaderPanel` and every other Job-UI-scope file must contain zero `job_type` conditionals** — gating is entirely a function of `job.retry_blocked` (present/absent), `job.retried_as_job_id` (already-exists check), and `capability.state` (mutations-off check).
- **`JobDetail` gains `retried_as_job_id: string | null`** (reverse of `retry_of_job_id`, derived at read time per D-20) — both fields already named in CONTEXT D-20 as required for lineage display; pinned here as an explicit type-contract addition since `types.ts` today has neither `retry_of_job_id` nor `retried_as_job_id`.
- **`JobFailureReason` (TS union, `types.ts`) gains `"domain_conflict"`** as a new closed-enum member, mirroring the backend's new `JobFailureReason.domain_conflict`.
- **`JobTypeCatalogItem.submission_defaults` stays typed `Record<string, string>`** — the `symbols` default for `ingest-bars`/`sync-symbol-metadata` is transmitted as a single **comma-separated string** (e.g. `"AAPL,MSFT,SPY"`), not a JSON array, so the existing type does not need widening. The comma-separated string populates the editable text field **only**. On submit, the form splits the field value on `,`, trims each entry, upper-cases it, drops empties, de-duplicates, sorts, and sends `symbols` as a JSON **`string[]`** (never a string) — the wire payload must match D-24/D-25 (`symbols: [...]` under `extra="forbid"`); a string-typed `symbols` would 422. An empty resulting array is blocked client-side (submit button disabled, helper text `At least one symbol is required`) since `symbols` is required.
- **Control routes must always return a structured `{"detail": {"code": ..., ...}}` body for every rejection, including body-shape/target-value validation** — mirroring the existing `api/routes/jobs.py:63-64` `_error()` helper pattern, not FastAPI's default `RequestValidationError` handler (verified: no custom `RequestValidationError` handler exists in `api/`, so an unguarded pydantic body-validation failure returns `{"detail": [...]}`, a list, which the console's `{code: ...}` dispatch cannot read). Concretely: the control routes must validate `state`/`status`/`reason` themselves (as a dependency or in-handler check) and raise `HTTPException(422, detail={"code": "invalid_control_target" | "invalid_control_reason", ...})` rather than relying on a pydantic `Literal[...]` field to produce FastAPI's automatic array-shaped 422. The existing `404` pattern (`resolve_strategy_metadata`, `detail=str(exc)`, a plain string) stays as-is — the console renders a plain-string `detail` verbatim (already the existing `ErrorState`/ fetch-client behavior), and only switches to the `{code: ...}` mapping table when `detail` is an object. Any other shape (e.g. an array, if this contract is violated) falls through to the defensive fallback copy in the Control-route error copy table above — the console must never crash on an unexpected `detail` shape.
- **Control mutation client functions (`tripKillSwitch`/`resetKillSwitch`/`enableStrategy`/`disableStrategy`, or equivalent, all added to `lib/api.ts`) send NO `Idempotency-Key` header** (D-10 — these are idempotent by explicit target state, not by key). This is a structural difference from `submitJob`/`cancelJob`/`retryJob`, which all require one.

### Retry mutation mechanics (D-20, fully pinned — was previously unpinned)
Mirrors `CancelJobDialog`'s existing mechanics exactly: one `Idempotency-Key` generated per dialog opening (`crypto.randomUUID()`), reused across every confirm attempt within that opening (including a transport-failure retry). On `202` (fresh submission): call `onNavigate(`/jobs/${result.data.job_id}`)` immediately. On `200` + `Idempotency-Replayed: true` (exact replay): show `Already submitted — opening existing Job` and call `onNavigate` to the same `job_id` immediately after (matches `BacktestJobForm`'s existing replay handling verbatim — the message is transient since navigation follows at once). On any error (409/422/etc.): the dialog stays open, shows the mapped plain-text copy from the Retry rejection table above, and triggers a Job-detail refetch (so `retried_as_job_id`/`retry_blocked` are fresh once the operator dismisses) — it does **not** auto-navigate or auto-close.

### Retry gating precedence (D-20) — never branches on `job_type`
Evaluate in this order and show the first that applies, using only generic, job-type-agnostic fields: (1) mutations disabled (`capability.state !== "enabled"`) — (2) `job.retried_as_job_id !== null` (a retry already exists) — (3) `job.retry_blocked !== null` (server-derived D-19 block, see API contract dependency above). Never show more than one disabled-reason message at once; the client-side check is UX-only — the 409 responses in the error-copy table above are the enforcement backstop for a stale view.

### Shared Control confirmation dialog — one component, four call sites
Build exactly one `ControlConfirmDialog` component (or equivalently named), reused verbatim across all four call sites (`/controls` Kill Switch section, `/controls` Strategy section, inline on `KillSwitchBanner`, inline on `/strategy`) — this is what CONTEXT D-13 means by "one shared confirmation-dialog component." It must NOT be four separate copy-pasted dialogs. Props: `currentState`, `targetState`, `actionLabel` (heading/confirm text), `requiresTypedConfirmation?: "RESET"` (only passed for the kill-switch reset call site), `onConfirm(reason: string) => Promise<{ changed: boolean; ... }>`. Implementation follows the exact same plain React-state overlay pattern as `CancelJobDialog` (`role="dialog"`, `aria-modal="true"`, `zinc-950/80` backdrop, `zinc-900` panel, `zinc-800` border) — do not introduce the native `<dialog>` element, for the same jsdom-testability reason documented in `19-UI-SPEC.md`. Sends no `Idempotency-Key` (see API contract dependency above).
