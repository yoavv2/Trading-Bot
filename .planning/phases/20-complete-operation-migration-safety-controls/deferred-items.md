- **20-18: caller constraint for `KillSwitchControlTrigger`/`StrategyControlTrigger` mounting (binding on Plans 22/23).** Both triggers now snapshot their dialog's state (`openedAsTripped`/`openedAsEnabled`) only at the moment their own button is clicked, so a live prop flip while the dialog is open no longer rewrites the D-14 "Already {STATE}" unchanged notice underneath the operator (fixed in this plan, see the `fix(20-18)` commit). That fix cannot protect a trigger that gets **unmounted** while its dialog is open: if the caller renders the trigger at a JSX position that is conditional on the same piece of state the trigger controls (e.g. `KillSwitchBanner`'s separate armed-branch vs. tripped-branch JSX, or a `result?.ok && <Trigger/>` guard whose `result` briefly disagrees with `isTripped`/`enabled` mid-refetch), a `changed: false` response's `killswitch:changed`/`strategy:changed` dispatch can cause the caller to re-render into the *other* branch, unmounting the trigger (and its open dialog) entirely — the operator never sees the unchanged notice at all, snapshot fix or not. (Note: `useApiQuery`'s `refetch` does NOT null out `result` while a request is in flight — verified by reading `src/lib/useApiQuery.ts`'s `runFetch`, `setResult` is only called once the new response lands — so a `result?.ok` guard does not itself cause a null-flash unmount; the risk is specifically a *branch* that keys off the same boolean the trigger's dialog is mid-flow on.) **Constraint for Plans 22/23:** each of the four call sites (`/controls` Kill Switch, `/controls` Strategy, inline `KillSwitchBanner`, inline `/strategy`) must mount its `KillSwitchControlTrigger`/`StrategyControlTrigger` instance at one stable JSX tree position that does not itself branch on `isTripped`/`enabled` (or on the same query's `result` while a mutation for that same domain could be in flight) — pass the boolean down as a prop, don't use it to pick between two different mount points.
