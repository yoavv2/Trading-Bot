<objective>
Close UAT gap 4. All 25 of the 25 OPERATOR_CONTROL runs in the live DB have completed_at < started_at (as far off as -93 ms). The cause is in services/operator_controls.py: `changed_at = datetime.now(UTC)` is taken in Python BEFORE the transaction opens, and started_at is Postgres `now()`, the transaction start, which is always later. Per locked user decision 4, the fix is:
- take one DB clock reading (`clock_timestamp()`) inside the transaction, after the row lock;
- use it for completed_at, event_at, last_changed_at and result_summary.changed_at;
- pin the fix with Postgres regression tests, including a lock-wait variant.

Purpose: control audit rows must be temporally consistent, since UAT tests 1, 2, 4 and 5 rely on them as the audit trail.
Output: the service fix, tests/test_operator_control_timestamps.py, and the D-11a line in 20-CONTEXT.md.

Independence: this plan is a leaf. No other plan depends on it, so the user may drop it without affecting 20-25, 20-26 or 20-27. Its depends_on 20-25 exists ONLY to order edits to the shared doc 20-CONTEXT.md, not for code. If 20-25 is dropped, remove the dependency and set wave 1.

It is still an open user decision (rewrite audit history, NOT VALID, or no constraint), so this plan adds NO migration and NO constraint, and no must-have claims DB-level enforcement. The executor records it in the SUMMARY under "Deferred / open decisions". The legacy inverted rows are left as they are.

Out of scope: other run types, which also mix clocks but are ordered by accident. Record this in the SUMMARY as a residual.
