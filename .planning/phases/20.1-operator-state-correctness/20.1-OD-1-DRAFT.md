## Decisions the user must make before this can run

1. **H2: does End or lazy expiry count as revocation?** May End (M12) or lazy expiry count as the operation-row revocation of C2? A takeover by a Continue/retry executor satisfies C2 without End.
   - If **no**: a Job whose operation was ended or expired, and never taken over, stays blocked.
   - If **yes**: End becomes one link in an evidence chain whose result is a release. The runbook rule "End is not a release" would have to be reworded to: End alone never releases, but End plus the zero-attempt evidence of C3/C4 establishes `nothing_submitted` after a fresh clean M5.
2. **H6: do Jobs created before migration 0029 qualify?** Before 0029, attempt rows and operation links could still have been deleted or truncated.
   - Default proposal: they do not qualify.
   - That means C4 is extended with "J's operation link and run were created after the 0029 upgrade". This needs the upgrade time to be recorded; the alembic_version row does not hold a timestamp. Otherwise the user accepts the DB history as intact.

## Proposed behaviour if approved

A flagged paper-session Job J with a linked paper_execution run and no attributed order is classified **`nothing_submitted`** instead of `unresolved / execution_path_unproven` only when **all** of the following hold:

- **C1:** J is terminal.
- **C2:** no execution_operations row names J as `executor_job_id`. The H2 decision determines whether End or expiry may have produced this state.
- **C3:** no attempt row has `executor_job_id = J`. This is already implied by "no attributed order".
- **C4:** an `execution_operation_jobs` row links J to an operation, subject to the H6 decision.

The usual fresh clean standalone reconciliation is still required (C6).

In every other case the state stays blocked exactly as today. Legacy orders (TL-4(a)) and ambiguous or unfinished submissions are untouched.
