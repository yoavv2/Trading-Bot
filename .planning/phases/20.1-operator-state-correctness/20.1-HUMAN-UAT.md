### Step 0 (MANDATORY before procedure 1): read-only inventory of non-terminal orders

Decision D-G1-A (user, 2026-10-06) makes this step mandatory before any real-stack UAT: it is read-only, it contacts no broker, it runs BEFORE the Alembic upgrade that brings the database to the head named in the preconditions (the query works at revision 0021 and at head), and no listed order is ever edited, deleted, cancelled, resubmitted or overridden.

1. Record the database revision (read-only): `PYTHONPATH=src .venv/bin/alembic current`.
2. Run the query below in a read-only session, for example `PGOPTIONS='-c default_transaction_read_only=on' psql "<dev database URL>" -v ON_ERROR_STOP=1 -f <file holding the query>`. The query sits between the two marker comment lines below (the start marker above the fence, the end marker under it) and is exactly:

<!-- uat-inventory-sql:start -->
```sql
SELECT s.strategy_id AS strategy, po.id AS paper_order_id, po.client_order_id,
       po.status::text AS status, po.broker_order_id, po.submission_attempt_count,
       po.created_at, sr.run_type::text AS origin_run_type, sr.job_id AS origin_job_id
  FROM paper_orders po
  JOIN strategy_runs sr ON sr.id = po.strategy_run_id
  JOIN strategies s ON s.id = sr.strategy_id
 WHERE po.status::text IN ('pending_submission', 'submission_failed', 'submitted',
                           'partially_filled', 'unknown')
 ORDER BY po.created_at, po.id;
```
<!-- uat-inventory-sql:end -->

3. How to read each row. A row is a REVIEW ITEM, not a verdict: the inventory itself produces no reconciliation finding and no outcome classification; after the upgrade those come only from the product (M5 findings, the recovery classification) and depend on what the broker returns. A listed row therefore does not by itself make a clean account M5 impossible; it is the reason for the review. By status:
   - `pending_submission` / `submission_failed` without a broker id: at revision 0021 the attempt log (0023) and operation intents (0027) do not exist, so the order is a legacy order; after the upgrade its shared verdict is `unestablished` (TL-4): the recovery classification blocks its strategy (`outcome_unresolved`) and A5, and while the broker does not return its client_order_id every reconciliation that loads it (its strategy's M5 and every account M5) reports it `MISSING_BROKER`, so no account M5 is clean (A6 refuses every ownership change; account-level uncertain Jobs such as the 29 Sep `broker-order-sync` Job stay unresolved; an owner's sends pause while such an account M5 is its newest standalone reconciliation).
   - `pending_submission` / `submission_failed` with a broker id: the verdict is `broker_evidence`; the order is reported `MISSING_BROKER` only if the broker does not return that id (then the same account-wide effect, while A5 may pass); if the broker returns it, the reconciliation compares the states.
   - `submitted` / `partially_filled`: a known active order, compared with the broker as before G-1; if the broker returns it in the expected state there is no finding, and only a broker account that does not know it reports `MISSING_BROKER`.
   - `unknown`: the recovery classification blocks its strategy and A5 (`outcome_unresolved`, TL-4); it never produces a `MISSING_BROKER` finding.
4. The STOP rule (a conservative review stop): if the query returns ANY row, stop before procedure 1 and send the result and the revision of item 1 to the user; the UAT continues only after the user's explicit decision; with no row, continue. The stop is a review gate, distinct from a reconciliation finding and from an unresolved-outcome classification; inventory results never authorize an edit, delete, cancel, override or resubmission of any order.

### TL-10 expectations (read through the Phase 20.1 surfaces)

An order that was accepted (in any later state, including partially filled), broker-rejected at
submission or uncertain consumes the allowance for its (strategy, evaluation session, symbol, side).

- While a submission is still uncertain, the stronger TL-4 block applies first: a new paper session is
  refused 409 `outcome_unresolved` and no per-candidate disposition is produced.
- Once it is resolved (found at the broker), the allowance stays consumed.
- For an accepted or broker-rejected order (or a resolved formerly uncertain one), a later evaluation
  of the SAME evaluation session yields the candidate disposition `action_already_submitted`, or
  `replay_of_earlier_decision` when its decision fingerprint is unchanged (that check runs first), with
  zero new orders. A fully filled entry or exit instead shows `duplicate_open_position` /
  `no_open_position`, because the strategy-semantics check runs before the allowance. The dispositions
  are in the paper-session Job and run results: `GET /api/v1/jobs/{id}` and `GET /api/v1/runs/{run_id}`
  (`result_summary.candidate_dispositions`).
- An intent proven not sent (`expired_unsent`, `cancelled_unsent`, or every attempt `pre_connection` /
  `deadline_expired`) does NOT consume the allowance: End the operation (M12), re-evaluate (M8) and a
  new session (M10) may send that action. Read the intent states in `GET /api/v1/execution-operations/{id}`.

### TL-11 expectations (read through the Phase 20.1 surfaces)

Partial-fill remainders are not pursued automatically.

- `GET /api/v1/operations/orders` shows the order's requested quantity and terminal status;
  `GET /api/v1/operations/fills` shows its filled quantity (the existing orders read has no
  filled-quantity field); `GET /api/v1/operations/positions` shows the retained remainder.
- The remainder is included in every later risk check. A partial BUY is never topped up.
- A later exit depends on the strategy: `trend_following_daily` and `time_series_momentum_daily` exit on
  the next session whose exit condition holds; `donchian_breakout_daily` and `rsi_mean_reversion_daily`
  may hold the remainder until their exit condition fires again.
- The partially filled EXIT case: a sell that fills only part and then expires leaves the remainder in
  the positions read, and another sell of that symbol in the same evaluation session is NOT offered. A
  re-evaluation of that session shows `action_already_submitted` when its fingerprint changed, or
  `replay_of_earlier_decision` when nothing changed, with zero new orders either way. The remainder
  can be sold only by a later evaluation session's exit, so it cannot be sold again in the same
  evaluation session.

Because partial fills, broker rejections and uncertain outcomes cannot be forced on the real paper
account, each such step is **"observe if it occurs"**; its automated proof is named instead:
20.1-15 A3 (including the PARTIAL EXIT case) and `test_partial_exit_remainder_per_strategy`, 20.1-15 A4,
20.1-15 A6 `test_broker_rejected_action_consumes_allowance_despite_changed_fingerprint` and N1, and the
20.1-13 scenarios E7 and E8 (`tests/test_phase20_1_api_e2e.py`).
