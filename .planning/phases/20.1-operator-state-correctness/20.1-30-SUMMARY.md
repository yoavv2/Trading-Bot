# Phase 20.1 Plan 30: CR-01 required regressions (c) genuine ambiguity and (d) consumer agreement Summary

**A genuinely ambiguous earlier attempt (NULL outcome, recorded read timeout, or an ambiguous attempt by the retrying Continue Job) stays `outcome_unresolved` through a fresh clean reconciliation, a refused Continue, a refused M15 retry of every flagged Job, End and a refused new start with zero new POST and zero new attempt rows, and the shared agreement assertion plus explicit per-checkpoint assertions hold for Continue, M15 retry of a Continue Job, new start after End and the ambiguous retry.**

## What is injected and what is a product path

Same rules as 20.1-29. Injected only: a worker crash before / around T1 (a worker held at `_send_authorized` or at the broker, its session-lock connection terminated) and the passage of time (a lease lapses by an UPDATE of `jobs.lease_expires_at`, explicitly `T - 1 minute`). Every Job becomes `outcome_uncertain` through the product sweep `reclaim_lost_jobs(now=T)` (each helper asserts the sweep reclaimed exactly that Job, FAILED, flagged, `completed_at == T`). Product entrypoints for the rest: `run_paper_order_submission` (start), `run_paper_continuation` (Continue), `JobOrchestrationService.retry` (M15), `claim_next_job`, `end_operation` (M12), `sync_account_state` (M4, counting lookup broker, zero POST), `apply_job_transition`, the submit gates `_continue_validate` / `_validate`, `takeover` (service-level S1 takeover). No `finish_jobs()`, `reclaim_job`, `probe_send` or direct write to `paper_orders`, `order_events`, `order_submission_attempts`, `execution_operations`, `execution_operation_intents` (grep gate clean; migration 0029 would reject it). The clean standalone reconciliation (M5) is seeded with `seed_account_run(session, completed_at=<Timeline instant>)`; every ordering is asserted next to the gate value. The start Job used by (c) and (d) carries the REAL start payload (the empty-payload `start_job()` would make the M15 retry fail with `InvalidRetryPayloadError` before the recovery block).

## Regression (c): `test_c_genuine_ambiguity_stays_blocked`

Per shape: (i) gate before any new reconciliation, (ii) after a clean M5 completed after every Job (A5 fails and its `evidence_refs` contain `RECOVERY_INTENT` O), (iii) `_continue_conflict` and M15 `retry` of every flagged Job, (iv) End then the same refusals again plus R3, (vi) a fresh evaluation start refused after End, (vii) global snapshots (`broker.received` dict, EVERY attempt row) unchanged, (viii) `assert_recovery_consumers_agree` after (i), (ii), (iv), (vi).

| Shape | POSTs before / after the assertions | Attempt rows | Gate at (i) / (ii) / (iv) / (vi) | Refusals (exact) |
|---|---|---|---|---|
| `null_outcome` (T1 committed, worker held before the request, lock killed, Job reclaimed) | `{}` / `{}`; after teardown release the held worker's ONE already-authorized request lands: `{cid1: 1}` | `(1, NULL)` unchanged; after release `(1, "ambiguous")`, never accepted | outcome_unresolved x4 | Continue `outcome_unresolved` (open and terminated operation); M15 retry of J1 `RetryBlockedError` code `outcome_unresolved`; new start `outcome_unresolved`; no retry Job created |

## S14 pin (`test_d_s14_unknown_order_with_a_complete_pre_connection_history[continue|end]`)

Product path of `test_s1_v2`: worker A held before its request leaves the process, A's Job reclaimed, the takeover executor B parks the intent UNKNOWN, A's request then fails `pre_connection` (`received == {}`, history `[(1, pre_connection)]`, no attempt #2); B finishes at an explicit instant. OBSERVED CURRENT behaviour:

- Strategy gate `reconciliation_required` (not `outcome_unresolved`); strategy status, account status, R3(J1) (`not_sent`, non-blocking, `resubmission_permitted: false`) and A5 (fails) agree; the shared assertion holds.
- The operation read model: `unresolved_intents == []`, intent 1 DISPLAYS `ambiguous` (intent 2 `planned`), operation `paused / outcome_unresolved`. Continue is refused `reconciliation_required`.
- After a clean M5 after every Job: gate None, A5 passes, the shared assertion holds, while the order is still UNKNOWN and still displayed `ambiguous`; the Continue submit gate ADMITS the operation. `continue`: the run POSTs only the later intent (intent 2 under `create_new`) and the UNKNOWN order is never POSTed and gets no new attempt row; `end`: End lists no unresolved intent, cancels only intent 2 (`cancelled_unsent`) and leaves intent 1 `ambiguous`.
- Pinned unconditionally (safety): the UNKNOWN order is never POSTed, its attempt rows do not change and its status stays UNKNOWN.

**OPEN display / gate mismatch (not fixed, not approved; same as 20.1-28 deviation 4):** the gate and A5 treat the order as proven not sent and release after a clean reconciliation, yet the operation read model and End do not list it, the intent still displays `ambiguous`, the operation still reads `paused / outcome_unresolved` and the order is neither re-sendable (never POSTed) nor resolved to SUBMISSION_FAILED until a broker sync establishes it.
