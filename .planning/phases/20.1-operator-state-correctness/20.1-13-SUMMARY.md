## Deviations from Plan

### Reported SPEC CONFLICTS (assertions kept strict; the product behaviour is asserted as it is)

1. **E1 first code.** 05 E1 names `strategy_not_active_paper_strategy` for the no-owner start; CONTEXT D-03 and 04 P20.1-01 name `no_active_paper_strategy`, which is asserted. The second code is asserted once another strategy owns the account.
2. **E3 second refusal.** After the broker fills the order and BEFORE a sync, the platform cannot know about the fill: the order is still locally non-terminal, so Continue is 409 `working_order_commitments_unaccounted`. `awaiting_reconciliation` is asserted after the account sync and before the clean reconciliation.
3. **E15 console half.** 05 E15 is a console-rendering scenario; this gate is HTTP-only. The API facts the console renders are asserted; the console half is the 20.1-14 vitest suite (passed).
4. **E9 `reconciliation_not_clean`.** The plan text names a submit-time 409 `reconciliation_not_clean` for a start while unrecognized activity exists. That code is a recovery gate code that applies only while an uncertain outcome exists (D-15). With unrecognized activity and no uncertain outcome the start is accepted (202) and refused at run time: the Job's in-session reconciliation blocks it (`action: blocked_reconciliation`), no operation is created, zero POSTs. Asserted exactly so.

### Observations for the owner of the product (no code changed here)

- **Account-scope sync after a fill.** An ACCOUNT-scope `broker-order-sync` never creates a Position (D-09 / ACCT-01), so after an owned order fills, an account sync followed by an account reconciliation reports the broker position as a blocking `MISSING_LOCAL` finding, and a Continue run then pauses `reconciliation_blocking` (pinned in `test_e4_immediately_filled_order`). 05 M4 / procedure 2 say "account or owner"; for fills only the OWNER-scope sync makes the reconciliation clean. E3, E4, E5, E6, E7, E8-C, E11, E12 and E13 therefore use the owner-scope sync (`settle()`); the account-scope sync is used where no owned fill exists (E1, E2, E15) and the UAT script says so. This is the one place the plan's scenario wording ("account sync + reconciliation") could not be followed literally.
- **Submit-time Continue gate checks only that a standalone reconciliation EXISTS after the latest effect, not that it is clean;** an unclean one is caught at run time (`reconciliation_blocking` / `unrecognized_broker_activity` pause). Observed while probing E3; not changed.
- **E8 ordering.** After the clock moves to the next trading day an unended operation reads `terminated/evaluation_superseded` lazily; End therefore runs inside the window in the base E8 test (so `cancelled_by_operator` is exercised) and the post-close part asserts the recovery blocking and the still-listed ambiguous intent.
- **`candidate_dispositions`** appears in the Job result only on the blocked and no-op paths; on a normal sending path it is `[]`, so E6 asserts the TL-10 effect on the broker POST list (the already-submitted action is not sent again) rather than a disposition value.

## Stop-and-report items (decisions the owner needs)

1. **Account-scope sync after a fill (cross-plan inconsistency).** The literal E3 / E4 step "account sync + account reconciliation -> Continue proceeds" cannot pass: an ACCOUNT-scope `broker-order-sync` never creates a Position (D-09 / ACCT-01), so the account reconciliation reports the broker position as a blocking `MISSING_LOCAL`, and a Continue run pauses `reconciliation_blocking`. 05 M4 and procedures 2 and 6 tell the operator "account or owner" scope. The gate uses the OWNER-scope sync after fills and `test_e4_immediately_filled_order` pins the account-path stall as CURRENT behaviour (its docstring says a product decision may change it). Decision needed: either amend 05 (owner-scope sync after an owned fill) or let the account path make owned fills reconcile clean.
2. **E9 `reconciliation_not_clean` cannot be a submit-time 409 as the plan text says.** It is a recovery gate code that applies only with an uncertain outcome (D-15). With unrecognized activity and no uncertain outcome the start is accepted (202) and refused at run time (`blocked_reconciliation`, zero POSTs, no operation). The Job read is truthful (`outcome` `blocked`, `outcome_reason` `reconciliation`, `operation` null), so this is not a COMPAT-01 truthfulness gap. Decision needed: keep run-time refusal and amend 05 M10 / E9, or add a submit-time unclean-reconciliation refusal.
3. **S3-R4 skip assertion not isolatable in E8 variant C.** Before the clean reconciliation the recovery gate answers `reconciliation_required` / `outcome_unresolved` ahead of `evaluation_basis_unverified`, so the skipped-reconciliation 409 is asserted in E6, E11 and E13 (day-2 exit session) instead; E9 and E12 start the strategy's first session (no earlier PaperOrders, so S3-R4 does not apply).

Unowned gaps recorded by earlier plans stand unchanged (legacy zero-attempt `pending_submission` order unassessed by the recovery predicate; an `ambiguous` order whose Job is not flagged `outcome_uncertain` invisible to the predicate until takeover or sync; `load_ownership_periods` prior-owner periods; the `default_strategy_id` report-only fallback). E13 deliberately does not run a reconciliation after the handover (the prior-owner gap). No scenario failed and no `xfail` was needed.
