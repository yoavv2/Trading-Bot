Design notes recorded here (implementation choices; interpretations are reported in the SUMMARY):
- S1-R3 submission authority, takeover and the actual guarantee (approved round 3, 2026-10-03; amended round 5, 2026-10-04: no resend while the original may still execute, proven-not-sent defined; authoritative; supersedes any wording in this plan set that implies the database guard makes the broker request atomic). (1) Authority and the attempt record are established durably BEFORE the POST, in ONE committed transaction T1 run by the single send path (20.1-15): lock the operation row FOR UPDATE; require state running, execution_epoch = the executor's epoch and executor_job_id = its Job; require the Job's lease (jobs.lease_owner = this worker, lease_expires_at > now); require the intent sendable by BROKER CERTAINTY, not by whether outcome fields are filled: the 20.1-02 submission class over ALL of the intent's attempts must be None or not_sent (every attempt ESTABLISHED as not sent: pre_connection or deadline_expired with a complete outcome); any attempt whose outcome is empty, ambiguous (timeout, 5xx, transport error after connect), exists_reported, accepted or rejected makes the intent not sendable, and the 20.1-10 recovery predicate must not report it unresolved; there is NO exception (round 5, 2026-10-04: the statement-backed resend is unavailable in this version). PROVEN NOT SENT (round 5, precise): an attempt is proven not sent only by POSITIVE evidence that its request never left the process, recorded by the executor that created it: outcome class `pre_connection` (the HTTP client raised httpx.ConnectError, ConnectTimeout or PoolTimeout, which occur before a connection exists and therefore before any request byte is written; 20.1-02 classify_attempt_exception) or `deadline_expired` (the wall-clock check refused to hand the request to the HTTP client). A NULL outcome (crash, suspension, lost process), a timeout or transport error after connect, a 5xx/429, exists_reported, accepted or rejected is NOT proof; a missing outcome is uncertainty. An intent is proven not sent only when EVERY attempt in its whole history (all operations, sessions and versions of that client_order_id) is proven not sent; zero attempt rows counts ONLY for an intent registered under the attempt-log invariant (it is operation-bound, i.e. has an execution_operation_intents row, or it has at least one attempt row), because G3 makes a POST without an earlier committed attempt row impossible only for such intents. A LEGACY order (registered before the attempt log: no attempt rows and no operation, e.g. every Phase 20 order) is NEVER proven not sent: it is established only by broker evidence (broker_order_id, a broker-applied status or fills); without that evidence a legacy UNKNOWN or PENDING_SUBMISSION order is unestablished (recovered like any never-found order), and a legacy SUBMISSION_FAILED order keeps Phase 20's classification for the uncertainty gate but counts as 'reached or may have reached the broker' for replay detection, the session allowance and version + 1. REACHED OR MAY HAVE REACHED THE BROKER (used by S3-R4) = any attempt not proven not sent, OR broker evidence on the order (broker_order_id, a broker-applied status, fills), OR a legacy order without proof. One proven-not-sent attempt never resolves an earlier or later ambiguous attempt of the same intent (classify_submission precedence: ambiguous wins); insert the 20.1-02 begin-attempt row (outcome NULL, carrying the epoch and Job id); set last_guarded_at; commit. The POST happens only after T1 commits; if T1 fails nothing is sent. EVERY HTTP attempt, including the in-loop retries after a `pre_connection` failure, needs its own T1: `begin_attempt` is callable only inside T1 (it fails closed otherwise), so an executor that lost authority cannot open attempt #2 after a refused connection (review round 3 follow-up, 2026-10-03). T1 also stores `authorization_deadline` = T1 commit time (database clock) + `send_authorization_ttl_seconds` (default 5) on the attempt row and returns the executor's local wall-clock deadline (local wall time at commit + the same TTL); immediately before handing the request to httpx the send path re-reads the WALL clock (never a monotonic clock, which stops during system sleep) and, if the deadline has passed, sends nothing and completes the attempt as established not-sent (`deadline_expired`), so a process suspended between T1 and the deadline check sends nothing; a suspension AFTER the check is not covered (L5). Because T1 holds the operation row lock, two executors' T1s for one operation serialize, and the second sees the first's attempt row and refuses because that attempt is not established as not sent. (2) The unavoidable race: after T1 commits, the executor may lose its lock connection, lease or epoch and still send that one POST; Alpaca does not know the fencing token and the platform cannot stop or cancel the request. (3) Takeover (20.1-16): acquire the session advisory lock, then commit the epoch CAS (epoch + 1, executor_job_id = new Job), and only AFTER that commit read the operation's attempt rows. Every intent whose submission class is not None/not_sent (an attempt with an empty outcome, OR a recorded ambiguous outcome such as a timeout, OR exists_reported) is IN DOUBT: its order is set UNKNOWN (ambiguous) and the operation becomes paused/outcome_unresolved. In-doubt is a property of the durable attempt row, not of any executor, so it holds whether the old POST was never sent, is still in flight or was accepted. (4) Why no request can follow while the original may still execute: rule (1) refuses T1 whenever the intent is not proven not sent, and Continue, new starts and handover (A5) are refused by the recovery gate while the intent is unresolved. There is NO path to resend an in-doubt intent in this version (round 5, 2026-10-04): resubmission would need proof that the already-recorded request can no longer reach the broker and produce an execution, and no available mechanism provides it: terminating the executor does not retract a request that has already left the process; a broker non-receipt statement and the absence evidence (a)-(d) show only that the broker has not (yet) seen it; elapsed time and deadlines bound nothing (L5); client_order_id uniqueness is not a fence (L3). The intent therefore stays unresolved until broker evidence establishes it (found_verified by client_order_id in any state, H-1; or a recorded broker 4xx rejection) or its own executor's late completion proves it not sent; a broker statement is retained as audited evidence only. Until then the strategy is blocked (outcome_unresolved) and neither End, lazy expiry, re-evaluation, a new operation, a new intent version nor an ownership change (handover/release/seeding check A5) bypasses the block (setting send_authorization_ttl_seconds lives in core/settings.py, added by 20.1-15). (5) Late outcomes: the old executor may still complete ITS attempt row (complete-once, only while the outcome is NULL; the attempt row is evidence, not authority) and writes an ExecutionEvent `late_attempt_outcome` with what the broker returned. Every other write of an executor (operation state, reason, intent dispositions, the best-effort pause, PaperOrder status) is a compare-and-set on execution_epoch and executor_job_id and affects 0 rows once it is stale. Order state is then established only by broker-order-sync and recovery (found by client_order_id and verified, H-1), never by the stale executor. GUARANTEE: (G1) every attempt is durably recorded before its request can leave the process; (G2) while any submission of the strategy may still produce an execution (an attempt that is neither proven not sent nor established by broker evidence), no other request is authorized for that strategy: not a retry of that intent, not a new intent, not a new version, under any operation, evaluation or owner (T1, the outcome_unresolved submit and run-time gates, and handover check A5); (G-late, a separate statement) the one durably recorded original request may still reach the broker late; that is a boundary of the platform, not a duplicate, because nothing else is sent while it may still execute; (G3') an executor that has lost authority cannot START a new attempt (its next T1 fails), so it has at most the ONE request it had already recorded; the deadline check stops that request only if the process notices the expiry BEFORE handing it to the HTTP client and cannot bound when an already-handed-off request leaves the process; (G3) every POST is preceded by a durable attempt row, so no POST is ever unknown to recovery. LIMITATIONS (stated, not hidden): (L1) the platform cannot prevent that one late POST from reaching the broker after takeover and has no cancel path, so it can create a live order and exposure; (L2) until sync and recovery classify it, the strategy is blocked (outcome_unresolved), which stops new submissions but not the late order itself; (L3) Alpaca rejects a duplicate client_order_id only for another active order, so the broker is not a second fence and is not relied on; (L4) a kill-switch trip does not stop an in-flight POST; (L5) a process can be suspended for an unbounded time between the final deadline check and the request leaving the socket, so that one recorded request can reach the broker arbitrarily late; the deadline narrows the window but bounds nothing; (L6) consequently a never-found in-doubt submission blocks the strategy (and, through A5, every ownership change) until the broker shows the order or the executor's own record proves it not sent; there is no product-level release in this version (accepted temporary limitation TL-4, round 5, 2026-10-04). Worker and database clocks are assumed to agree (NTP); skew can only change when a deadline check refuses, never authorize a second request. This is duplicate-SUBMISSION prevention, not prevention of every late broker action. End and lazy expiry also increment execution_epoch and clear executor_job_id, so no stale fenced write can touch a final operation. Storage (approved): execution_operations.executor_job_id (the Job that currently holds execution authority; NULL when none), execution_epoch (monotonic fencing token, incremented by every takeover; carried by T1 and by every executor write), last_guarded_at (time of the latest successful T1; diagnostics and the stale-executor audit). The attempt row additionally records the epoch, the Job id and the authorization_deadline that created it (columns added to the 20.1-02 table by migration 0027).
- S2-R3 pre-send price (approved round 3, 2026-10-03). Every pre-send risk check (start and Continue, held and not-held symbols) uses a fresh broker price; the evaluation price (`reference_price`) is only the sizing basis, the deviation baseline and audit. Source: Alpaca Market Data v2 latest trade, read-only `GET {alpaca_data_base_url}/v2/stocks/{symbol}/trades/latest?feed={price_feed}` through `AlpacaClient.get_latest_trade(symbol)` (GET retries like every other GET; never a POST); fields used: `trade.p` (price, Decimal, must be > 0) and `trade.t` (trade timestamp, RFC 3339, converted to UTC).
