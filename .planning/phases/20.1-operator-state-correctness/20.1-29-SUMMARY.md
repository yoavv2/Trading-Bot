# Phase 20.1 Plan 29: CR-01 required end-to-end regressions Summary

**The CR-01 fix is proven on the real reuse paths: after a SAF-01 release, Continue, an M15 retry of a crashed Continue Job and a new Start each re-register the earlier zero-attempt order with `retry_existing`, POST it exactly once, keep its origin run, never leave a registering Job `execution_path_unproven`, and the strategy gate is never `outcome_unresolved`.**

## What is injected and what is a product path

Injected (only): a worker crash before transaction T1 (a worker held in a wrapper around `submit_orders._send_authorized` whose session-lock connection is terminated, or a one-shot exception before `authorize_send`) and the passage of time (a Job's lease lapses by an UPDATE of `jobs.lease_expires_at`). Product entrypoints for everything else: `reclaim_lost_jobs` (the only way a Job becomes FAILED / outcome_uncertain), `run_paper_continuation`, `run_paper_order_submission` (start domain call), `JobOrchestrationService.retry` (M15), `claim_next_job` (worker claim), `end_operation` (M12), `sync_account_state` (M4, a counting lookup broker, zero POST), `apply_job_transition` (a Job finishing at an explicit instant). No `finish_jobs()`, no `_recover_by_client_order_id`, no direct write to `paper_orders`, `order_events`, `order_submission_attempts`, `execution_operations`, `execution_operation_intents` (grep gate clean; migration 0029 would reject it anyway). The clean standalone reconciliation (M5) and the M8 verified-basis evaluation are seeded (reconciliation via `seed_account_run(session, completed_at=<explicit>)`, evaluation via the existing `evaluation()` helper); every ordering relation (Job.completed_at vs reconciliation.completed_at) is asserted at its checkpoint.

## Harness choices (no fallback to the harness `reclaim_job`)

- Jobs are crashed with the product sweep `reclaim_lost_jobs(session, now=<explicit>)` after the lease is lapsed by an UPDATE; the helper asserts the sweep reclaimed exactly the target Job and that `completed_at` equals the explicit instant. `reclaim_job` / `finish_jobs` are not used.
- The start Job is built by the module (real start payload, RUNNING, lease) because `start_job()` seeds `payload={}`, which an M15 retry (`validate_payload`) would reject; the retried Job is claimed with the product `claim_next_job`.
- The R3 / operation reads run against a module-local `http` fixture on the same `migrated_paper_db` (the shared `http` fixture creates a second database).
- Mutation check (temporary, reverted, `src` clean afterwards): restricting the order-event attribution in `recovery._order_registered_on_run_sql` to `intent_registered` makes (b1) fail with "Job ... registered an order yet reads execution_path_unproven"; re-adding `pending_order.strategy_run_id = run_id` in `register()` makes (a) and the rest fail on the 0029 origin-immutability trigger.
