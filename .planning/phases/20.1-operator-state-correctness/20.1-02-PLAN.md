<objective>
Deliver COR-06 (D-12, D-13; E-3, R-17, R-22): an ambiguous order submission is never automatically re-sent and never silently downgraded to a retryable failure. Every HTTP attempt of an order POST is logged durably before and after it; the submission class is computed over all attempts; an ambiguous outcome parks the intent in `UNKNOWN` and makes the Job `outcome_uncertain`; a duplicate-id reply triggers a lookup, never an inference; and the Alpaca status mapping becomes a closed, tested table (`done_for_day` working, `replaced` terminal-with-successor, unmapped -> unknown with a reason).

Purpose: today `AlpacaClient._request_with_retry` re-sends POST /v2/orders on any transport error or 5xx/429 (an order that reached Alpaca but timed out is re-sent), and `submit_orders.py:481-505` turns every submission exception into a retryable `submission_failed`. Recovery (20.1-10) and the execution operation (20.1-11) both read this plan's attempt log and taxonomy.
Wave 2 / depends_on ["20.1-01"]: (a) migration chain `0022 -> 0023` (this plan owns 0023 and needs 20.1-01's 0022 as `down_revision`), and (b) the shared file `services/execution/submit_orders.py`, which 20.1-01 edits first (ownership gates, explicit strategy_id) and this plan edits second (submission loop). Wave-2 sibling 20.1-04 shares no file with this plan.
Output: migration 0023 + model; `services/execution/attempts.py`; single-attempt submit path and GET lookup in the Alpaca client; ambiguous/rejected handling and the pre-send guard in the submission loop; closed status table; migration, taxonomy, persistence, status-table and Job-level tests.
</objective>
