<investigation id="OD-1">
## OD-1 investigation (user request 2026-10-05): can durable positive evidence plus revoked executor authority prove that an order-less flagged paper-session Job submitted nothing and can submit nothing?

Scope: a flagged (outcome_uncertain) paper-session Job J (start or Continue) with a linked paper_execution run and NO attributed order (after 20.1-26: no order originates on its runs, no accepted intent_registered / retry_requested order_events row on its runs, no attempt row with executor_job_id = J). Today: Job-level `unresolved / execution_path_unproven`, blocking, no product release.

Evidence chain (code read 2026-10-05 at base 2693b48):
1. The only HTTP order POST in src is `AlpacaClient.submit_order` (alpaca.py ~:580-620); it raises `AttemptLogNotBoundError` unless an attempt log is bound, and calls `log.begin_attempt()` before every HTTP attempt.
2. The only binder in src is `bind_attempt_log(log)` at submit_orders.py ~:2845 inside `_send_authorized`, binding a `GuardedAttemptLog` created only AFTER `operations.authorize_send` (T1) committed; its later attempts each run their own T1. `DbSubmissionAttemptLog.begin_attempt` raises `AttemptNotAuthorizedError` outside `send_authorization_scope` (attempts.py ~:456-463). So every POST is preceded by a committed attempt row carrying `executor_job_id` (G3).
3. T1 locks the operation row FOR UPDATE first, then requires `state = running`, `execution_epoch == epoch`, `executor_job_id == J`, and J's lease (`status RUNNING`, lease_owner, `lease_expires_at > db now`), and requires the order to exist (registered) (operations.py ~:1603-1760).
4. `_executor_identity` raises without a Job id (no Job-less executor exists in src).
5. After 20.1-27 attempt rows, orders, order_events, operation rows, intents and operation-Job links cannot be deleted, updated (where guarded) or truncated.

Exact conditions under which J is provably "nothing submitted and nothing can still be submitted":
- C1 J is terminal (FAILED / CANCELLED / SUCCEEDED; the closed Job lifecycle never returns a Job to RUNNING).
- C2 J's execution authority has been REVOKED BY AN OPERATION-ROW WRITE that is committed and observed: for every execution_operations row, `executor_job_id IS DISTINCT FROM J` (takeover by a Continue/retry executor bumps the epoch and replaces the executor; End and lazy expiry clear it). Because T1 serializes on the same row lock, any T1 of J either committed before that write (its attempt row is then visible) or refuses afterwards.
- C3 No attempt row with executor_job_id = J, read in the same snapshot as C2 or later (already implied by "no attributed order", because the attempt arm attributes any such attempt).
- C4 J belongs to the attempt-log era: an `execution_operation_jobs` row links J to an operation (written only by 20.1-11+ code), so G3 applied to J.
- C5 The code invariant of steps 1-2 holds and is pinned by a source/AST test (one POST site, one binder, binder only after T1).
- C6 A fresh clean standalone reconciliation after the latest broker-touching effect (unchanged requirement for every nothing_submitted).

Holes (every one found):
- H1 Job status alone is NOT revocation: T1 reads J's lease without locking the Job row, so a T1 whose lease check ran before the reclaim committed can still commit an attempt after J is FAILED. Only C2 (an operation-row write under the T1 lock) closes this race. A J whose operation still names it as executor stays blocked until a takeover, End or expiry.
- H2 End / expiry as revocation: if C2 is satisfied by End (M12) or lazy expiry, End becomes a link in an evidence chain that ends in release. That conflicts with the standing rule "End is not a release" (D-20 and the user's 2026-10-05 instruction). A takeover by a Continue/retry executor satisfies C2 without End, but for a J whose operation was ended (or expired) the rule would need End to count. USER DECISION REQUIRED.
- H3 Era boundary: a flagged paper-session Job with a run but no operation link (pre-attempt-log Jobs, or a start Job blocked before `create_operation`) cannot be told apart durably; it must stay blocked (C4 fails). No product release for those.
- H4 Atomicity of the link: C4 relies on the link row existing whenever J could hold authority. VERIFIED 2026-10-05 (read, base 2693b48): `create_operation` adds the `start` ExecutionOperationJob in the same caller-owned transaction as the operation row that names J as executor (operations.py ~:880-945); `begin_continuation` / `adopt_running_operation` insert the continue / resume link (~:1042-1130) before `acquire_execution` sets `executor_job_id` in a later committed transaction (~:1436-1480). The optional plan pins this with a source test; any future change that grants authority before the link breaks OD-1.
- H5 Future code: any new POST path or binder outside T1 silently breaks the chain; C5's pin is mandatory and must fail the build.
- H6 Evidence erasure before 0029: a database where attempt rows or links were deleted or truncated before 0029 cannot prove C3/C4; acceptable only for rows created after 0029 (or a DB whose history is known intact). USER DECISION REQUIRED on whether pre-0029 Jobs qualify.
- H7 Lease and clocks: not relied on (C2 is lock-ordered, not time-based); no hole.
- H8 Broker side: G3 makes a POST without an attempt row impossible within this process model; a request already handed to httpx always has its committed attempt row (then the Job is not order-less). No hole within the stated model; the model itself (single POST site) is C5.

Result: the chain HOLDS under C1-C6, with two points that need the user (H2: whether End / expiry may serve as the revocation; H6: whether pre-0029 Jobs qualify); H4 verified in code. Per the user's instruction it is drafted as a SEPARATE optional plan, `.planning/phases/20.1-operator-state-correctness/20.1-OD-1-DRAFT.md` (deliberately NOT named *-PLAN.md so execute-phase does not pick it up), tagged pending user decision OD-1, not executed by default and not part of 20.1-26..31. Until OD-1 is decided, `test_d_order_less_flagged_job_stays_blocked_while_od1_is_open` asserts the state stays blocked.
</investigation>
