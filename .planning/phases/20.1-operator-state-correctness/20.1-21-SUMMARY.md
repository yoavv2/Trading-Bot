# Phase 20.1 Plan 21: One D-07 identity check for every binder; exit quantity = whole position Summary

**A same-client_order_id broker record with a different symbol, side, quantity, type or earlier created_at is no longer bound to an unresolved local intent by the bulk sync or the pre-lock recovery (REVIEW SAF-07), and a sell that is not exactly the verified position is refused with `exit_quantity_mismatch` at intent creation (REVIEW SAF-08).**

## Accomplishments

- `broker_record_mismatch(order, ticker, snapshot)` in `services/execution/broker_identity.py` (field order unchanged: client_order_id, symbol, side, quantity, type, created_at). `recovery._lookup_mismatch` delegates to it.
- `_sync_paper_orders` (used by `sync_paper_state`, `sync_account_state` and the recovery applier) and `recover_inflight_paper_orders` run the check before binding a broker id to a local order with none. On a mismatch: `continue` (no broker id, no status transition, no field update) plus an ExecutionEvent `broker_order_identity_mismatch` (severity error, blocks_execution true, details field / client_order_id / broker_order_id / broker_symbol). The strategy stays `outcome_unresolved`, also after a later clean reconciliation.
- `classify_candidate` step (5): after `held <= 0 -> no_open_position`, a sell with `quantity != held` (Decimal compare) returns `exit_quantity_mismatch`. Buys, held 0 and basis-less (hand-seeded) runs are unchanged.

## Residual risk

- A real broker list whose typed `created_at` is absent and whose payload lacks `created_at` is refused (`created_at`) when the local order has a registration time, same as the already-deployed lookup rule. Alpaca payloads carry `created_at`; a missing one is treated as unverifiable, not as a match.
- The mismatch event is recorded once per sync pass per order that still has no broker id; a persistent collision repeats the (idempotent, blocking) event every pass.
- `held` for the exit comparison is the evaluation basis position (`rows.basis_positions`); KNOWN-2 (account-path sync not opening Position rows) is out of scope here and unchanged.
- ExecutionEvent insertion happens inside the sync session; if a later step of that same sync raises, the session rolls back and the event is lost (the order is still not bound).
