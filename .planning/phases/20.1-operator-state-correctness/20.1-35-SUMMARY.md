## What each test pins

- **Matrix.** Against a broker that holds no order: the 9 explained shapes (PROVEN_NOT_SENT x6, REJECTED x3) produce no finding in any pass; the 15 others (UNESTABLISHED x14 incl. the four ambiguity-dominance shapes `failed_ambiguous_then_rejected`, `pending_unfinished_then_rejected`, `pending_rejected_then_unfinished`, `failed_duplicate_reported_then_rejected`, and BROKER_EVIDENCE `failed_with_broker_id`) produce exactly one MISSING_BROKER, whose own `blocks_execution` is true, severity `error`, and whose details `submission_evidence` equals the expected verdict. The control (UNKNOWN + ambiguous) produces nothing (unchanged), is not explained by the verdict (UNESTABLISHED) and is listed as a BLOCKING intent by `strategy_recovery_status` (order-specific: the gate code alone is already set by earlier shapes in the shared database).
- **Oracle.** For each of the 24 shapes the presence of the finding equals `load_strategy_order_facts(...)` verdict `not in {PROVEN_NOT_SENT, REJECTED}`, and the details carry the oracle's verdict value (the oracle's own verdict is also asserted equal to the shared table).
- **Corrections.** After the in-session pass and `apply_reconciliation_corrections(OWNER, report=report)`: `sync_failure_count` 0 for `op_bound_pending_count1_no_attempts` and `pending_rejected` (no error, no failure stamp), 1 for `legacy_pending_count1` (error = the finding message).
- **Broker returns an explained order.** A broker order with the client_order_id and the identity (same symbol, side, quantity, order type, created after the registration) of a proven or a rejected order yields exactly `["STATE_MISMATCH"]` for that order in every pass, the finding blocks, and attribution flags no anomaly for it (so the twin is a real same-identity record).
- **Unrecognized broker order.** Next to an explained order: no finding for the order, exactly one blocking MISSING_LOCAL for the unknown broker order id (non-platform client id, another symbol), listed as the only unrecognized order, report blocks.
- **Scopes.** OWNER has a proven and a rejected order, OTHER a legacy pending order, plus an OWNER legacy control. OWNER's strategy pass (both trigger sources) names only the control; OTHER's own strategy pass names only OTHER's order; the account pass names OTHER's order and the control and, among the three scenario orders, only OTHER's.
- **Threshold.** For `failed_pre_connection_deadline_expired` (PROVEN_NOT_SENT) and `failed_pre_connection_then_rejected` (REJECTED): below the threshold the stored result has no entry for the order; with `submission_attempt_count` set to `repeated_failure_threshold` there is still no finding, but `result_summary["threshold_breach"]` (strategy run row / account run row) holds one `submission_failure_threshold_exceeded` entry naming the order with that count.

## The identity-mismatch blocking mechanism observed

Observed first (scratch script, nothing committed), then pinned: for BOTH a quantity mismatch (broker 11, local 10) and a symbol mismatch (broker MSFT, local AAPL), with the broker order sharing a proven order's client_order_id, in ALL three passes:

1. `recover_inflight_paper_orders` returns 0; the order stays `pending_submission` with `broker_order_id` and `broker_status` None and no order event (no broker acknowledgement applied).
2. Exactly one `broker_order_identity_mismatch` ExecutionEvent is persisted by `record_identity_mismatch` on the order's own origin run: severity `error`, `blocks_execution` true, details `{field: "quantity"|"symbol", client_order_id, broker_order_id, broker_symbol}`, message naming the broker order id and `its <field> differs`.
3. The following strategy-scope and account-scope reports block through **both** mechanisms: a blocking **STATE_MISMATCH finding** naming the order (local `pending_submission` vs broker `accepted`, expected local status `submitted`) **and** an **attribution anomaly `owned_order_attribute_mismatch`** naming the broker order (no unrecognized order, no unexplained exposure). The order is still unbound afterwards.

## Deviations from Plan

None under Rules 1-4: no product defect was found, every assertion passed against the product as it is, none was weakened and no src file or existing test was touched. Adaptations inside the plan's own file:

1. **Module database fixture.** The plan names `migrated_database(monkeypatch, ...)`; a module-scoped fixture cannot take the function-scoped `monkeypatch`, so the fixture owns a `pytest.MonkeyPatch()` (the pattern of `test_trading_blockers.py` and `test_account_basis_freshness.py`), and also sets the dotenv `env_file` to None for its own scope (it is built before the autouse `isolate_operator_env`), so nothing in this module can load the operator's `.env`.
2. **Threshold test parametrization.** `[pass x explained]` (6 nodes) instead of `[explained]` alone, and each node also runs the below-threshold evaluation first so the counter is the proven cause of the added entry.
3. **Extra controls and pins inside the listed tests** (no scope change): an OWNER legacy control order and OTHER's own strategy pass in the scopes test; the in-session pass in the identity follow-ups; exactly one identity event and zero order events; the same-identity twin is anomaly-free; the control's verdict is asserted not explained; and `test_matrix_is_the_agreed_set`.
4. **Tracking.** The plan's `<output>` says not to edit STATE.md, but the orchestrator's success criteria and the user's binding instructions call for the standard tracking update, so STATE.md and ROADMAP.md are hand-edited in the metadata commit as in 20.1-32 / 33 / 34 (the `gsd-sdk` roadmap and state verbs were not used: known column-shift and wrong-value bugs). ROADMAP guard checked: one `20.1.` row, 5 cells, `35/37`, status `In Progress (gap closure r3 executing)`, the Phase 20.1 checkbox still unchecked.
