# Phase 20.1 Plan 22: Continue sends only the pinned identity; an unparseable accepted reply is uncertain Summary

**Continue now asserts, before any registration write and before T1, that the identity it would send equals the pinned intent row (REVIEW SAF-03), and a broker-accepted order whose 2xx reply cannot be normalized is parked UNKNOWN with the Job outcome_uncertain instead of being recorded as a clean failure (REVIEW SAF-06).**

## Accomplishments

- `_assert_pinned_identity(session, view, decision, candidate)` is the first statement after the decision is resolved in `register()`. Fixed order symbol, side, quantity (Decimal `==`), client_order_id; the first differing field raises `PinnedIdentityMismatchError(field, pinned, derived)`, rolling the registration transaction back (no PaperOrder, no `_link_intent`, no event, no `state.existing_orders` append).
- `_refuse_pinned_identity_mismatch`: one fenced write records the ExecutionEvent `pinned_identity_mismatch` (severity warning, non-blocking, details field / pinned / derived / intent_id), then `_move_running(REQUIRES_REEVALUATION, evaluation_data_changed | strategy_settings_changed, "pinned_identity_mismatch:<field>")`; the loop returns without raising, so the Job is not failed.
- `OrderIntent` is built from the view: `client_order_id=view.client_order_id`, `symbol=view.symbol`, `side=OrderSide(view.side)`, `quantity=view.quantity`.
- alpaca.py: `_normalize_accepted_reply` wraps the accepted-path and duplicate-record normalization; `_resolve_duplicate_reply` maps an unparseable lookup reply to `invalid_response_body`. Docstring note added. `submit_orders.py` generic `except Exception`: duplicated `failure_error = exc` removed, "no broker side effect is known" comment replaced by the attempt-history statement.

## Behaviour changes on the send path

- Continue / Start with a drifted symbol, side, quantity or client_order_id (prefix setting change, mutated risk event) now sends ZERO POST and requires re-evaluation (previously: sent a different identity than pinned, or, for create_new_version, failed the Job).
- The order sent is always the pinned identity (view), not the rebuilt candidate.
- A 2xx whose body cannot be normalized, or a duplicate-reply lookup whose record cannot be read, is `AmbiguousOrderSubmissionError(invalid_response_body)`: order UNKNOWN, operation paused outcome_unresolved, exception propagates (Job failed, outcome_uncertain), never re-POSTed. Previously it fell into the generic branch as SUBMISSION_FAILED (retryable, a re-send risk for a possibly live order).
- No send-side or identity check was relaxed.
