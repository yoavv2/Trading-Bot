<objective>
Close the CR-01 BLOCKER (VERIFICATION gap SC5 / REC-02, SAF-01 closure, REC-01 / PAPER-02 liveness) the way the user required on 2026-10-05: preserve DURABLE HISTORICAL LINKAGE between an order, the run/Job that first registered it, and every later run/Job that registered or retried it, so moving or reusing an order never erases the earlier Job's evidence and never manufactures new uncertainty.

Root cause (REVIEW CR-01, reproduced by the orchestrator): `register()` executes `pending_order.strategy_run_id = run_id` (submit_orders.py ~:2437) for `retry_existing`; the recovery predicate attributes orders to a flagged Job only through `po.strategy_run_id = sr.id` (or an attempt by that Job), so the flagged SAF-01 Job is left with a run and zero orders -> `execution_path_unproven` (a blocking state with no product release today), permanently blocking T1, Continue and A5.

Why BOTH halves (deleting the assignment alone is not enough): register() commits its `retry_requested` row in its own fenced transaction BEFORE T1. A Continue / retry Job that crashes between registration and T1 would, without a history arm, be left with a run and zero orders: CR-01 moved to the next Job, i.e. new uncertainty. So: (1) the origin is immutable (assignment deleted; 20.1-27 makes it a DB invariant); (2) every later registering run is read from the order_events registration rows that already exist (no new table, no backfill, and orders re-parented before this fix are re-attributed from the rows they already have); (3) the attempt row names the run that sent it.

Planner evaluation of storage (user asked to evaluate a migration): no new table is needed; `order_events` already records every registration with its run, written in the same transaction as the registration. Migration 0029 (20.1-27, wave 2, after this plan) only adds triggers (origin immutable, order_events append-only, TRUNCATE guard). It must land AFTER this plan, otherwise every retry_existing registration would hit the trigger.

Purpose: the SAF-01 release survives Continue / retry / new start. Output: the src fix, the shared agreement helper, the permanent repro and the linkage regression module.

Requirement coverage note: this gap set (20.1-26..31) touches only REC-01, REC-02, PAPER-02 and COR-06; PAPER-01, ACCT-01, EXT-01, COR-01, COR-03, COR-04, COR-05, PROV-01 and COMPAT-01 are covered by the executed plans 20.1-01..25 and are not re-planned here.

V-2 DECIDED (user, 2026-10-05): keep `order_events` as the registration history, with durable evidence protection (20.1-27, migration 0029: order_events append-only and undeletable, evidence rows protected against direct and parent-cascade DELETE and against TRUNCATE incl. CASCADE). No new history table. On the read side the history source is named in ONE place, the function `_order_registered_on_run_sql` added in Task 2. Skipping the history arm is not an option: without it a Continue / retry Job that crashes between its committed registration and T1 is left with a run and no orders and becomes `execution_path_unproven`, i.e. CR-01 moved to the next Job (user decision 1: no new uncertainty).

Known read consequence (deferred to Phase 21 read models): with an immutable origin, the legacy run-level reads in `services/operator_reads.py` (`get_run_detail` `artifact_counts.paper_orders` / `paper_fills` at ~:176-188 and `list_paper_orders` at ~:194-215, both joined through `PaperOrder.strategy_run_id`) attribute a Continue / retry / new-start order to its ORIGIN run, so the Continue run shows 0 orders although it sent the order (before the fix the origin run lost it instead). This plan pins the new behaviour with one read test and does not change the reads; registration-aware run reads belong to the Phase 21 read models.
</objective>
