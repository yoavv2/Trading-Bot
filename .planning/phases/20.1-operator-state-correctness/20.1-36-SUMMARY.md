## What each test pins

- **Legacy order** (INSERT-seeded with the existing legacy helpers: no attempt row, no operation intent, no broker id): the REAL reconciliation of either scope reports exactly one MISSING_BROKER with `details["submission_evidence"] == "unestablished"`, the finding itself blocks and so does the report; the gate is `outcome_unresolved` before AND after the reconciliation (it never releases it) and A5 fails; a Start through `run_paper_session` returns `blocked_outcome_unresolved` with zero broker reads (counting read client), zero POST, no new `paper_orders` row and no new `order_submission_attempts` row, the order unchanged.

- **Ambiguous submission** (product read-timeout shape: attempt `(1, ambiguous)`, order UNKNOWN, one POST): with the order visible at the broker the account reconciliation reports a blocking STATE_MISMATCH naming the order; with nothing visible it reports NO finding and the whole report is CLEAN (`blocks_execution` False, `finding_count` 0), exactly as before G-1, and that clean report still resolves nothing. ## Deviations from Plan

None under Rules 1-4: no product defect was found, every assertion of the plan passed against the product as it is, none was weakened, no src file or existing test was touched. Wording and design points inside the plan's own file:

1. **[Rule 1 - plan wording] "A6 is then the only failing check" (test 7, step 6, broker-id order).** Observed: `A1, A6`. A1 fails with `open_operation` on the OWNER's own operation, which step 7 (Continue) needs to stay open, and A1 reads no reconciliation evidence. A2 to A4 pass. So the sentence holds among the checks that read reconciliation or recovery evidence (A5 passes, A6 fails), not literally across A1..A6. Every claim the user enumerated holds (account M5 not clean only for the other strategy's order, owner gate `reconciliation_not_clean` then None after a real owner-scope M5, A6 keeps failing, A5 fails for the legacy order and passes for the broker-id order, Continue POSTs once). The exact sets `{A1, A5, A6}` / `{A1, A6}` and A1's reason and evidence (the owner's operation) are pinned instead of the literal sentence. Flagged for the orchestrator.
2. **[Test design] Fresh evaluations without a recorded basis.** The plan says "a fresh evaluation" and does not name a basis arrangement. The default basis writes a broker-order-sync Job at now + 1 min (a future broker effect) and a clean account reconciliation row (a seeded result); every refusal here is decided by the recovery gate before basis verification, so `evaluation(..., verified=False)` is used throughout and each Start observes the gate with `_GateSpy` (`spy.answers` equals the expected gate code, so a Start refused for another reason cannot pass).
3. **[Additions, no scope change]** a Start through `run_paper_session` was added to tests 2, 3 and 6 (the plan text had the submit-time validation, or Continue, only), because the plan's must-haves require "a fresh Start through run_paper_session" for every negative case; the Start in tests 4 to 6 uses the world's own `S1Broker` as the send side, so any POST would show in its `received`, and a counting read client with the same orders as the reconciliation's; test 3 `broker_shows_nothing` also pins the observed clean report; test 7 also asserts the owner's gate (None) and the cross-consumer agreement for OTHER after Continue.
4. **[Harness]** `record_property` carries the observed codes; the held worker of the unfinished test is released in a `finally` inside the test body (the plan said finalizer) so the thread ends while the database exists.
