## Narrative Findings (AI reviewer)

### Q1. No UPDATE path changes `job_type`, but the Job identity is mutable

**Guard 4 refuses every UPDATE form tested.**
- The column arm is `OLD.job_type::text = 'reconciliation' OR NEW.job_type::text = 'reconciliation'` (`0030:276-280`). It reads no table, so visibility and lock windows (a) and (b) are gone.
- The trigger is unchanged: `BEFORE UPDATE OF job_type ... WHEN (OLD.job_type IS DISTINCT FROM NEW.job_type)` (`0030:299-302`).
- Every rewrite of the forms in P1 still lists `job_type` among the target columns: `ON CONFLICT DO UPDATE`, row assignment, views and rules, CTEs.
- A NULL is refused by the trigger (23000) before NOT NULL is checked.
- The trigger is the only UPDATE trigger on `jobs` (P1 trigger list), so firing order is irrelevant.
- Creating a trigger, rule or child table on `jobs` needs ownership. `session_replication_role` needs a superuser, and the role is not one. COPY only inserts. MERGE does not exist on PostgreSQL 14.
- Look-alike types (case, whitespace) are not refused, but cannot qualify: the gate compares exactly (`latest.py:197`, `recovery.py:715`, C collation).

**Not closed: the identity.** The handler holds a Job *id*, and `jobs.id` is not frozen (P1 `SET id`; P4). See WR-02.

### Q2. Guards 1-3 mean what they meant; legitimate writers pass

**Every cast is meaning-preserving:**
- **enum -> text** (`0030:141`, `:186`): enum labels are unique per type, so label equality is equivalent to value equality.
- **varchar -> text** (`:180`, `:223-224`, `:229-230`, `:286`): varchar `=` already resolved to pg_catalog's `texteq` through a binary coercion.
- **NULLs:** `IS DISTINCT FROM` treats them identically.
- **Collation:** the database collation is C, which is deterministic.
- **Unchanged:** the `IN` lists, the uuid / timestamptz / date / boolean / integer / jsonb comparisons, and the json-to-jsonb casts.

**Writers:**
- `_update_reconciliation_run` (`report.py:973-1006`) and `account._finalize_run` write a pending run, so no freeze is armed and no link column is in the SET list.
- `reclaim_stale_runs` touches `paper_execution` runs only: guard 2's WHEN is false and guard 1 does not fire.
- Job lifecycle writes never write `job_type`. They are pinned by the e1 module (`:867-915`) and `test_legitimate_writers_still_work`.
- No code in `src` / `scripts` UPDATEs `jobs.job_type` or retypes a Job after creating it (grep). The only `.job_type =` hits are class attributes. `Job(` construction is INSERT only (`jobs/dependencies.py:196`).
- The operator documents (runbook 05, HUMAN-UAT) contain no manual retype.

## Warnings

### WR-01: The operator plant that the `::text` casts defend against also blinds the gate's own reader, releasing the gate with no row changed

**Files:**
- `src/trading_platform/services/recovery.py:714-715` (`_RECONCILIATION_SQL`: `sr.trigger_source = 'job'`, `rj.job_type = 'reconciliation'`, which are varchar = unknown literals), with the gate decision at `:1020-1058`.
- `src/trading_platform/services/reconciliation/latest.py:196-197`: SQLAlchemy's psycopg dialect has `render_bind_cast = True`, so `Job.job_type == ...` is sent as `varchar = $1::VARCHAR`.
- The deferral in `0030:100-103`.

**Issue.** PUBLIC holds CREATE on `public` (P1). The casts make every 0030 guard verdict immune to a planted operator, but the reader that the guards protect is not immune.
- A `public.=(varchar,varchar)` that is false only when one side is `'reconciliation'` is an exact match, so it wins over pg_catalog's `texteq`-by-coercion in every session whose path contains `public`.
- The strategy half of the gate then finds no standalone run, the older clean account run is the newest qualifying run, and the gate releases.
- Confirmed in P3: `reconciliation_not_clean` -> `None` -> `reconciliation_not_clean`, with the jobs table unchanged.
- The same plant also controls the J arm of the 0029 delete guard (residual (1)) and, through `j.job_type IN (...)` (`recovery.py:634`, `:687`), which Jobs count as flagged or effect Jobs.

**Effect.** The extra hardening is correct and load-bearing for the guards (P1 mutant), but it does not close the planted-operator threat it names. This route reaches the E1 effect more easily than any UPDATE route: one CREATE OPERATOR, reversible, and invisible in the data.

**Fix.** User decision. Add it to the OPEN same-class list; it is pre-existing and not introduced here. The only complete fix is the privilege change the 0030 docstring defers:
- `REVOKE CREATE ON SCHEMA public FROM PUBLIC;`
- `GRANT CREATE ON SCHEMA public TO <migration role>`. The schema owner is `yoavhevroni`, and the application role creates its tables through PUBLIC's grant today.
- Add a pin that `has_schema_privilege('public', 'CREATE')` is false for the runtime role.

Casting the reader's literals (`rj.job_type::text = ...`) closes only those two comparisons.

### WR-02: Window (a) is still reachable through the Job's key: an id swap retypes "Job X" without any job_type UPDATE and without inserting or deleting a Job

**Files:**
- `0030:299-302`: guard 4 fires on `UPDATE OF job_type` only.
- `jobs.id` has no guard.
- `job_events` / `job_logs` (`db/models/job_event.py:50`, `job_log.py:52`): their FKs are `ON UPDATE NO ACTION`, and neither table is protected against DELETE.
- `report.py:353` / `:361`: the pre-run window.

**Issue.** While the broker is read, the RUNNING reconciliation Job is referenced only by its own audit rows. An ordinary-DML client deletes those rows, then swaps ids with any existing non-reconciliation Job using three `UPDATE jobs SET id` statements. The run that `reconcile_paper_execution` inserts with the handler's `job_id` then hangs off a `backtest` Job, and the gate falls back to the older clean pair (P4: gate `None`).
- No `job_type` changes.
- No Job is inserted or deleted.
- Without the deletes, the key UPDATE fails with 23503 (P4).
- Window (b) should be safe: the key UPDATE needs `FOR UPDATE`, which waits for the FK's `FOR KEY SHARE`, and NO ACTION then refuses. This follows from lock semantics and was not exercised.

This is the identity-substitution class of residual (3), reached through UPDATE. It is not in the residual list. A later fix of (3) that only stops DELETE of reconciliation Jobs would leave it open.

**Fix.** User decision, together with residual (3). Freeze the key: a `BEFORE UPDATE OF id ON jobs ... WHEN (OLD.id IS DISTINCT FROM NEW.id)` trigger that always raises (no writer updates a primary key; grep before adding). Add a pre-run swap pin modelled on `test_e1a`.

### WR-03: The 0029 origin guard (CR-01 durable linkage) can be hijacked by reordering the caller's search path and planting `=(uuid,uuid)`; it is not in the residual list

**Files:**
- `0029:113-122`: `NEW.strategy_run_id IS DISTINCT FROM OLD.strategy_run_id`, unpinned.
- `0030:73-76`, `:312-319`: only the delete guard is pinned.
- `e1:126-133`: the `UNTOUCHED_FUNCTIONS` pin asserts `proconfig IS NULL` for the origin guard.

**Issue.** When the caller lists `public` before `pg_catalog`, an identical-signature `public.=(uuid,uuid)` wins. `paper_orders.strategy_run_id` is then re-pointed, so the order "moves" (P2: accepted; refused on the default path).
- The same attack fails against pinned guard 1 (P2).
- The user's instruction was to "cover the lookup functions of 0029". The implementation read that as *relation* lookups. This function performs an *operator* lookup that the caller controls.

**Fix.** User decision on scope only; the path itself is already decided.
- The user's path `pg_catalog, public, pg_temp` already closes WR-03: pinned guard 1 refuses the identical `=(uuid,uuid)` attack under it (P2), because pg_catalog's exact uuid operator comes first.
- So the fix is `ALTER FUNCTION paper_orders_origin_run_immutable() SET search_path = pg_catalog, public, pg_temp`, reset on downgrade, exactly as for the delete guard. It also updates the `UNTOUCHED_FUNCTIONS` pin.
- `pg_catalog, pg_temp` (without `public`) would also work, because the body references no relation. It is optional here and required only for WR-04.

### WR-04: Residual (2) is broader than stated: no search-path change is needed, and pinning to the 0030 path would not fix it

**Files:** `0028:74-99` (`to_jsonb(NEW) - ...` compared with `=`). The same construction appears in 0025 (`:109-123`) and 0026 (`:214-232`).

**Issue.**
- Function resolution prefers an exact argument-type match over a polymorphic one, whatever the schema order.
- So a `public.to_jsonb(public.order_submission_attempts)` returning `'{}'` beats `pg_catalog.to_jsonb(anyelement)` on the default path. It also wins under `pg_catalog, public, pg_temp`.
- With it, a completed AMBIGUOUS attempt is rewritten to `pre_connection` (P2). An unresolved, possibly-sent order then reads as not sent.
- The plant only loses when `public` is absent from the path (`pg_catalog, pg_temp`: refused).
- The author's form, an identical `=(jsonb,jsonb)` plus `public` first, is also confirmed.

**Fix.** Out of scope by decision. Record it accurately. When it is fixed, either pin these three functions to `search_path = pg_catalog, pg_temp` (their bodies reference no relation), or qualify `pg_catalog.to_jsonb` and `OPERATOR(pg_catalog.=)`. The same ALTER FUNCTION used for the delete guard would leave this open.

### IN-02: Guard 4's WHEN clause is bound when the migration runs; a varchar `=` planted beforehand disables the guard for good

**Files:** `0030:301` (`WHEN (OLD.job_type IS DISTINCT FROM NEW.job_type)`, uncast and unchanged by decision). The pin at `tests/test_phase20_1_evidence_update_guards_migration.py:445-460` checks substrings only.

**Issue.**
- On a clean database, the stored WHEN is `(old.job_type)::text IS DISTINCT FROM (new.job_type)::text` (P1).
- If `public.=(varchar,varchar)` already exists when 0030 runs, the WHEN binds to it (P5): it deparses uncast and has a normal dependency on the plant. With an always-equal plant, the trigger never fires.
- The plant cannot be dropped without CASCADE, and CASCADE would drop the trigger.
- The persistent dev database (said to be at 0021, with PUBLIC CREATE on `public`) still has to run 0030.
- Guard 2's WHEN already casts and is immune.
