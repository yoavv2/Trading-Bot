## Warnings

### WR-01: The run-to-Job link (`strategy_runs.job_id`, `run_type`) is still mutable, so CR-01-class detachment is one UPDATE away

**Files:**
- `alembic/versions/0029_phase20_1_order_origin_immutable.py:110-131` (only `paper_orders.strategy_run_id` is pinned) and `:164-208` (DELETE-only guards)
- `src/trading_platform/services/recovery.py:643`, `:650`, `:670-675`, `:711` (every attribution and reconciliation join goes through `sr.job_id` / `sr.run_type` / `rj.job_type`)
- `src/trading_platform/services/recovery.py:873-889` (a paper-session Job with `run_count == 0` becomes `NOTHING_SUBMITTED`, which is established)

**Issue:** 0029 makes the order's origin run durable, and makes runs and Jobs undeletable. The attribution chain continues through the next link, though: `paper_orders.strategy_run_id → strategy_runs.job_id → jobs`. That link is plain mutable data. Examples:

- `UPDATE strategy_runs SET job_id = NULL` (or another Job id) on the only `paper_execution` run of an ORDER-LESS flagged Job (the OD-1 shape, which must stay blocked).
  - `run_count` drops to 0, and the Job's `execution_path_unproven` entry becomes `NOTHING_SUBMITTED` (established).
  - The gate falls to `reconciliation_required` and is released by the next clean M5.
  - A detached run that had orders does not release anything: an UNESTABLISHED order always has a candidate status (pending/failed without a broker id, or unknown), so it falls into the unflagged branch and still blocks. The order-less Job is the exposure.
- `UPDATE strategy_runs SET run_type = 'backtest'` on the same run has the same effect. It also turns off guard R, so the run becomes deletable.
- The same holds for `strategy_runs.job_id` of a standalone reconciliation run (it drops out of `strategy_latest`), and for `account_reconciliation_runs.status / blocks_execution / completed_at`. In the latter case, a newer dirty run can be rewritten instead of deleted, which is the exact W4 scenario 0029 guards against for DELETE.

Verified: nothing in `src` writes `strategy_runs.job_id` or `run_type` after construction. The only writers are the constructors (`submit_orders.py:3515-3521`, `risk.py:793`, `operator_controls.py`, `backtesting.py:207`). So this is not a product path. It is the same "any DB client" threat model that motivated 0028 and 0029, and r2 rated the equivalent TRUNCATE hole (WR-07) as a WARNING.

**Fix:** Add column-immutability triggers in the 0029 style, in a new revision so that 0029 stays as reviewed:

```sql
CREATE FUNCTION strategy_runs_link_immutable() RETURNS trigger AS $$
BEGIN
  IF NEW.job_id IS DISTINCT FROM OLD.job_id
     OR NEW.run_type IS DISTINCT FROM OLD.run_type
     OR NEW.strategy_id IS DISTINCT FROM OLD.strategy_id THEN
    RAISE EXCEPTION 'strategy_runs job/run_type/strategy link is immutable'
      USING ERRCODE = 'integrity_constraint_violation';
  END IF;
  RETURN NEW;
END $$ LANGUAGE plpgsql;
CREATE TRIGGER trg_strategy_runs_link_immutable
  BEFORE UPDATE OF job_id, run_type, strategy_id ON strategy_runs
  FOR EACH ROW EXECUTE FUNCTION strategy_runs_link_immutable();
```

The `job_id` SET NULL from a Job delete stays reachable only for unprotected Job types. Either allow `NOT NULL → NULL` only when the referenced Job no longer exists, or accept the refusal: J already blocks it for every type the gate reads. Do the same for `jobs.job_type`. For `account_reconciliation_runs`, make it complete-once (`completed_at`, `status`, `blocks_execution` and `unresolved_reasons` frozen once `completed_at` is set). Then add a pin test that a single UPDATE of each column is refused.

### WR-02: The `register()` guard's UNKNOWN-park branch leaves the raising Job order-less, which makes it a permanent `execution_path_unproven` Job

> **Assessment note (user assessment, 2026-10-06):** Current evidence does **not** establish a product-reachable race for this finding. The seeded after-permission attempt row that the tests use (`seed_attempt_row` in the `after_permission` window) is a test arrangement, not proof that any product writer and interleaving can produce it. This finding therefore stays a **LATENT, fail-closed observation** (no send happens, the Job stays blocked) unless an actual writer and interleaving are demonstrated. It is **not** a mandatory fix for gap G-1 (reconciliation treating a never-sent `pending_submission` order as `MISSING_BROKER`). Wherever the analysis below says the race or the reachability is possible, read it as **"not established"**. The original analysis is kept unchanged below for the record.

**Files:**
- `src/trading_platform/services/execution/submit_orders.py:2466-2487` (UNESTABLISHED branch: `_park_intent_unknown`, then `return`, with no registration row and no `_link_intent`)
- `submit_orders.py:3762-3766` (the park writes `broker_status_unknown` on `run_id`)
- `submit_orders.py:2581-2586` (re-raises `AmbiguousOrderSubmissionError`). Verified that this flags the Job: `jobs/handlers/paper_session.py:77-82` logs `external_broker_session_started` before the service call. `AmbiguousOrderSubmissionError` is not in `DOMAIN_CONFLICT_OUTCOME_UNCERTAIN` (`domain_conflicts.py:49-56`), so the runner's HANDLER_ERROR path sets `outcome_uncertain=True` (`runner.py:339`, `:81-91`).
- `recovery.py:612-619` (only `intent_registered` / `retry_requested` attribute)
- `recovery.py:878-881` (a flagged paper-session Job with a run and no orders becomes UNRESOLVED / `execution_path_unproven`, with no release)

**Issue (pre-existing, not a regression of this diff):** the old guard also returned before the removed re-parent line, so this behaviour predates the diff. It is reported here because it is the CR-01 class (a Job that touched an order is not attributed to it) and the new attribution model does not cover it. When the guard sees an UNESTABLISHED history on the older order, it parks that order UNKNOWN on the CURRENT run and raises, which flags the current Job J. No `retry_requested` row was written, because the guard returns before the transition at `:2522-2535`. J made no attempt, so the executor arm does not match either. If that intent is the first one the operation registers, J's run has zero attributed orders, and J becomes a Job-level `execution_path_unproven` entry.

That entry stays even after the parked order is later `found_verified` and reconciled clean. The strategy is then blocked permanently, which is exactly the CR-01 outcome reached through a different door. The parked order is also not linked to the planned intent (`_link_intent` is not called), so the operation read model shows the intent as `planned` and never lists the order J parked.

Reachability is latent and **not established** (user assessment 2026-10-06; the seeded attempt row is not proof of a product-reachable race). 20.1-28 found the guard is reached only by the planned-intent-to-older-order shape. The UNESTABLISHED variant also needs attempt rows to be committed on the older order between NVDA's permission check and its registration. That is the `after_permission` window, which the tests arrange via `seed_attempt_row` (a seeded arrangement; a product writer for it is **not established**). I found no product writer that can do this for an order whose operation is terminated: T1 needs the fence, and `complete_attempt_late` only completes rows that already existed at permission time, and the gate would already have blocked on those. The tests do not catch it, because in `test_ambiguous_or_unfinished_history_dominates_a_rejection_and_is_never_posted[after_permission]` AAPL is registered on R2 first. J therefore has an order and is not order-less, and the test never asserts the Job-level entry.

**Fix:** Tie the parked order to the Job that parked it, and the problem disappears without changing OD-1. Either:

- (a) apply `RETRY_REQUESTED` (legal from pending and from failed) before `_park_intent_unknown` in the guard branch, so the existing fragment attributes it; or
- (b) add `broker_status_unknown` to the accepted event types in `_order_registered_on_run_sql`. I checked every other writer of this event, and none of them attributes an order to a new run:
  - takeover `_mark_unknown` (`operations.py:1542`), sync (`sync_orders.py:365`) and reconciliation (`report.py:847`) all write on the order's ORIGIN run;
  - the send-path writer (`submit_orders.py:2827`) and the send-path park (`:2673`) write on the current run, which already has a `retry_requested` / `intent_registered` row.

  (a) is still preferred because it keeps the history source to the registration rows.

Also call `_link_intent` in that branch. Add a regression where the guarded intent is the operation's FIRST intent: assert that J is not `execution_path_unproven`, and that after `found_verified` plus a clean M5 the gate is None.

**S14 safety analysis:**

1. **Shape.** An UNKNOWN order with a complete `pre_connection` history is PROVEN_NOT_SENT (`attempts.py:305-309`, attempts branch). The gate and A5 release it after a clean M5. The read model shows it `ambiguous`, and `unresolved_intents` omits it.
2. **Not sendable while UNKNOWN.**
   - UNKNOWN is never resubmittable (`submit_orders.py:3790-3798`), so a same-hash candidate gets `reuse_existing`, which pauses and sends nothing.
   - Continue skips it, because its state is AMBIGUOUS, which is not among the sendable states (`submit_orders.py:1956-1975`).
   - End does not cancel it, because `_UNSENT_STATES` is required (`operations.py:1153-1162`).

3. **Later POST through REC-01 only.** Only a broker-order-sync pass moves it from UNKNOWN to `submission_failed` (`recovery.py:1577-1600`, liveness). After that its state is NOT_SENT. A Continue or a same-session Start then chooses `retry_existing`. The guard reads PROVEN_NOT_SENT, T1 re-checks, and the order is POSTed exactly once. TL-10 is not consumed (`reached_broker` is False).
4. **Why that is sound.** Every attempt is a complete `pre_connection`, and the S1-R3 invariant rules out a POST without a committed attempt row. An in-doubt zombie worker cannot add an attempt, because every retry needs its own fenced T1.
5. **Verdict.** The display errs on the conservative side ("ambiguous", operation `paused/outcome_unresolved`). The only operator actions it invites (End, statement, wait) are no-ops for safety. The remaining risk is operator confusion, not an unsafe send.
