## Summary

The gap diff does what it says on the send path. I found no case where the code can POST after a refusal or ambiguity, or bind a broker id without a D-07 check on first binding:

- Every POST still needs a committed T1.
- T1 now re-reads the owner, kill switch, enabled flag, window and price age on every attempt. It does this with no lock on any gate row, so the lock order stays operation row, then order row.
- A refusal raised in a retry's T1 propagates out of `begin_attempt` (`alpaca.py:618`). That is outside the transport `try`, so it reaches `_SEND_REFUSAL_PAUSE`.
- An unparseable 2xx is now ambiguous.
- Continue sends the pinned view.
- The 0028 trigger accepts both production completion writers. No code in `src` deletes `paper_orders` or attempt rows.

The one blocking defect is in liveness, not send safety, and it defeats the purpose of SAF-01:

- The gate now releases an operation-bound zero-attempt order on a flagged Job once a clean reconciliation exists.
- The natural next step is Continue. Continue's registration re-parents the order to the Continue Job's own run (`submit_orders.py:2437`).
- The flagged Job is left with a run and zero orders, which is the TL-4 terminal state `execution_path_unproven`. Continue's T1 then refuses `outcome_unresolved` and the strategy is blocked permanently.
- I confirmed this with a scratch test against the real predicate (see CR-01). The SAF-01 test calls `authorize_send` directly and never registers through a new run, which is why the suite is green.

The warnings are:

- One classifier that was not migrated: the operation and End read model still use `derive_intent_state`.
- One binder that does not use the "one" D-07 function: the duplicate-reply lookup.
- An already-bound-order overwrite.
- Three freshness and settings inconsistencies in SAF-09.
- A TRUNCATE hole in 0028 (WR-07).
- A `retry_existing` guard that still disagrees with the shared verdict (WR-08).

Not re-reported, per the accepted residuals:

- Legacy zero-attempt orders gate until reconciliation finds them (TL-4).
- `execution_path_unproven` stays permanent for a Job that genuinely never registered an order.
- The legacy summary keys are missing for pauses that T1 catches.
- The 5 s T1-to-POST TTL bound.

## Critical Issues

### CR-01: The SAF-01 release path re-blocks the strategy permanently, because Continue re-parents the order and the flagged Job becomes `execution_path_unproven`

**Files:**
- `src/trading_platform/services/execution/submit_orders.py:2437` (`pending_order.strategy_run_id = run_id` for `retry_existing`)
- `src/trading_platform/services/recovery.py:610-614` (flagged-branch join through `po.strategy_run_id = sr.id`, or an attempt by `executor_job_id = f.id`)
- `src/trading_platform/services/recovery.py:826-832` (Job-level `execution_path_unproven`)
- `src/trading_platform/services/execution/operations.py:1717-1719` (T1's G2 read)

**Issue:** The SAF-01 shape is an operation-bound order O in `pending_submission` or `submission_failed`, with zero attempt rows. It sits on the `paper_execution` run R1 of a flagged Job J1 (lease loss before T1, or a non-refusal error inside T1). After 20.1-17, O classifies as `not_sent` and the gate falls to `reconciliation_required`. A clean reconciliation then clears it, so the operator can Continue. What happens next:

1. `run_paper_continuation` creates a new run R2 for the Continue Job J2 (`submit_orders.py:1185`).
2. For the pinned intent, `_resolve_paper_intent_decision` finds O by `intent_hash`. `_is_resubmittable_order` returns True for `pending_submission` and for `submission_failed` below the threshold, so the action is `retry_existing`.
3. `register()` sets `O.strategy_run_id = R2` and commits.
4. The predicate now finds R1 with zero orders. J1's executor never wrote an attempt (it died before T1), so the `EXISTS (... oa.executor_job_id = f.id)` arm does not match either.
5. J1 becomes a Job-level `UNRESOLVED / execution_path_unproven` entry. By design (SAF-04 / TL-4) nothing ever releases that.
6. J2's T1 calls `strategy_recovery_status`, gets `OUTCOME_UNRESOLVED`, and refuses. The operation pauses `outcome_unresolved`.

The strategy, A5 (seeding, handover, release) and every later Continue are now blocked permanently. That is the state SAF-01 was meant to remove ("needs DB surgery"). An M15 retry of J1 re-registers O under a new run in the same way.

**The amended runbook leads into it.** `.planning/research/operator-console-ia/05-INTERIM-API-OPERATIONS.md` procedure 3, branch B (line 75), says an operation-bound intent with no attempt row "is proven not sent". Step 4 (line 76) then says that after a clean fresh M5 "M10/M11 ... become eligible". M11 is Continue, which triggers this defect. The only safe action today is M12 End, followed by a clean M5. That leaves O on R1, and the next session's intents hash differently, so nothing re-parents O. That workaround is not written down anywhere.

**Evidence (empirical):** I ran a scratch test outside the repository, reusing the fixtures of `test_saf01_*`. It is reproduced below so it can be added as the missing test. Both parametrizations fail on the last assertion. The gate becomes `outcome_unresolved`, and the only intent is `{intent_id: None, classification: unresolved, unresolved_reason: execution_path_unproven, blocking: True}`.

```python
@pytest.mark.parametrize("status", [PENDING, FAILED])
def test_saf01_release_survives_continue_reregistration(shared_db: str, status) -> None:
    ids = {}

    def build(session):
        flagged = seed_job(session, completed_at=at(0))            # FAILED, outcome_uncertain
        run = seed_paper_run(session, flagged)                     # R1
        executor = seed_operation_job(session, status=JobStatus.RUNNING, lease_owner="worker-1",
                                      lease_expires_at=datetime(2100, 1, 1, tzinfo=UTC))
        operation = seed_operation(session, state="running", reason=None, epoch=3,
                                   executor_job=executor, jobs=[(executor, "start")])
        order = seed_operation_bound_intent(session, run, status=status, attempts=(),
                                            operation=operation)
        ids.update(order=order.id, executor=executor.id)

    _arrange(build)
    _arrange(lambda s: seed_account_run(s, completed_at=at(30)))
    assert _gate() is None                                          # passes (SAF-01 release)

    def reregister(session):                                        # what register() does
        run2 = seed_paper_run(session, session.get(Job, ids["executor"]))   # R2 of the Continue Job
        session.get(PaperOrder, ids["order"]).strategy_run_id = run2.id     # submit_orders.py:2437
        session.flush()

    _arrange(reregister)
    assert _gate() is None   # FAILS today: outcome_unresolved / execution_path_unproven for J1
```

**Why the suite is green:** `tests/test_recovery_shared_classifier.py:532-591` calls `ops.authorize_send(...)` directly with O still on the flagged Job's run. It never drives the Continue registration that re-parents O.

**Fix (preferred):** Stop re-parenting on `retry_existing` at `submit_orders.py:2437`. Keep `strategy_run_id` on the run that registered the order, and record the retrying run on the `RETRY_REQUESTED` order event, which already carries `strategy_run_id=run_id`. The existing `EXISTS (... oa.executor_job_id = f.id AND sr.id IS NOT NULL)` arm of the flagged join already ties a retried order to the retrying Job once that Job's T1 writes an attempt, so the retrying Job does not lose sight of the order.

**Alternative:** Attribute orders in the predicate by their registering run, for example an `order_events` EXISTS arm on `intent_registered` with `oe.strategy_run_id = sr.id`. If you take this route, apply the same attribution to BOTH `NOT EXISTS` clauses of the unflagged branch (`recovery.py:628-634`). Those clauses key on `po.strategy_run_id`, so without the change O would be listed twice once the retrying T1 writes an attempt: under J1 in the flagged branch, and again in the unflagged branch.

**Either way:**
- Add the test above.
- Add a test that drives `run_paper_continuation` after the clean reconciliation and asserts exactly one POST and gate `None`.
- Until the fix lands, amend runbook step 4 to say "End (M12), then M5; do not Continue" for this shape.

## Warnings

### WR-01: The operation read model and the End result still classify through `derive_intent_state`, which disagrees with the shared verdict

**Files:** `src/trading_platform/services/execution/attempts.py:210-240`, `operations.py:813-827`, `operations.py:1341`, `services/operation_reads.py:106`

**Issue:** 20.1-17 routed G2, takeover, basis verification and the predicate through `classify_submission_evidence`. `IntentFact.state` (`operations.py:650`, `:712`) is still `derive_intent_state`, and `operation_unresolved_intents` lists only `state is AMBIGUOUS`. Two shapes give a different answer than the gate:

- **DB-06 shape.** The attempt is `accepted` but the `accepted()` persist rolled back. The order is still `pending_submission` with no broker id.
  - `derive_intent_state` returns `SUBMITTED`.
  - `is_working_order` returns False because there is no broker id.
  - The operation view and `EndResult` therefore report zero working orders and zero unresolved intents.
  - The shared classifier says `UNESTABLISHED` and the strategy gate is `outcome_unresolved`.
- **Legacy reused zero-attempt order** (linked by a later intent, so `attempt_log_registered=False`).
  - `derive_intent_state` returns `REGISTERED_UNSENT`.
  - End does not cancel it, because `_unsent_facts` also requires `proven_not_sent`. That part is safe.
  - The End result still lists it nowhere, while A5 and the gate block on it.

This is not a send hazard, but the operator surface contradicts the gate, which is this phase's subject.

**Fix:** Derive `IntentFact.state` for the unresolved list from the shared verdict. Treat `classify_submission_evidence(...) is UNESTABLISHED` as unresolved. Either retire `derive_intent_state` or reduce it to a display mapping over `SubmissionEvidence`. Extend the 15-shape agreement test to cover `operation_unresolved_intents`.

### WR-02: The duplicate-reply binder does not use `broker_record_mismatch`

**Files:** `src/trading_platform/services/alpaca.py:504-538` (`_intent_mismatch`), `:813`; binding at `submit_orders.py:2728`

**Issue:** 20.1-21 says `broker_record_mismatch` is the one D-07 check for every binder. The fourth binder, the duplicate-reply lookup, still uses its own `_intent_mismatch`. The two checks read different fields:

| Field | `_intent_mismatch` | `broker_record_mismatch` |
|---|---|---|
| quantity, type | raw `qty` / `type` only | typed fields first, raw as fallback |
| registration time | treated as UTC | takes the broker's tzinfo |
| unparseable `created_at` | caught | not caught |

Today it is equally strict or stricter (raw-only), so it is not a bypass. But the checks will drift: any future relaxation or tightening of `broker_record_mismatch` silently skips this binder, which is the only one that binds a broker id on the send path. `broker_identity.py` imports `alpaca.BrokerOrderSnapshot`, which is why alpaca cannot simply call it.

**Fix:** Move `broker_record_mismatch` to a module with no dependency on alpaca, for example taking a minimal protocol of `client_order_id/symbol/side/quantity/order_type/created_at/raw_payload`, so `alpaca._resolve_duplicate_reply` can call it with the pinned intent's fields. Alternatively, add a parity test that runs both functions over the same mismatch matrix.

### WR-03: Already-bound orders are updated by client_order_id match without checking that the broker id matches

**Files:** `src/trading_platform/services/execution/sync_orders.py:333-379`, `src/trading_platform/services/reconciliation/report.py:197-217` and `:820-860`

**Issue:** Both binders look the broker record up by `client_order_id` first and fall back to `broker_order_id`. The SAF-07 guard runs only `if not local_order.broker_order_id`. When the local order is already bound to id X and the client_order_id lookup returns a record with id Y, the code still overwrites status transitions, `broker_status`, `filled_at`, `canceled_at` and `broker_payload` from Y. Nothing compares the two ids. This is exactly the id-collision case SAF-07 was about (a re-created DB against a reused paper account), seen from the bound side.

**Precondition (not demonstrated):** this path is reachable only if a broker listing returns a record whose client_order_id equals a bound local order's while its broker id differs. That means two broker records sharing one client_order_id, or a local order bound to the wrong id earlier. Alpaca rejects duplicate client_order_ids, so this is defence in depth, not an observed path.

**Fix:** When `local_order.broker_order_id` is set and differs from `broker_order.broker_order_id`, record `broker_order_identity_mismatch` with field `broker_order_id` and `continue`. Match by `broker_order_id` first for orders that are already bound.

### WR-04: SAF-09 basis verification fails open for a missing or unknown basis source

**Files:** `src/trading_platform/services/execution/intent_identity.py:286-293`; contrast `src/trading_platform/services/portfolio.py:98-110`

**Issue:** The two checks have opposite polarity:
- `verify_evaluation_basis` refuses only `basis_source == "configured_starting_cash"`, and checks staleness only when the source is `"broker_sync"`.
- `execution_basis_problem` refuses anything that is not `broker_sync`.

So a risk run with no `portfolio_basis`, a non-string source, or any other value passes basis verification: "judged by the old rules". The per-intent step 5 still checks the live snapshot at send time, so cash is not unchecked. But the evaluation-time sizing (the risk event's `proposed_quantity`) can come from a basis that was never shown to be broker-observed.

**Fix:** Fail closed on the same rule the permission step uses:

```python
if rows.basis_source != "broker_sync":
    return BasisVerification(BasisFailure.BASIS_NOT_BROKER_OBSERVED)
if rows.basis_age_seconds is None or rows.basis_age_seconds > rows.max_basis_age_seconds:
    return BasisVerification(BasisFailure.BASIS_STALE)
```

If hand-seeded runs need an escape, make it explicit in the fixtures rather than in production code.

### WR-05: The basis-age limit is read from the global settings cache, not the caller's settings

**Files:** `src/trading_platform/services/execution/intent_identity.py:625` (`load_settings().execution.account_snapshot_max_age_seconds`); contrast `permission.py:550-552` (`settings.execution...`)

**Issue:** The setting has two readers with two sources. `_prepare_start` and the executor run on `ctx.settings`. `load_basis_verification_rows` reads the `lru_cache`d `load_settings()`, and `portfolio.load_state_with_basis` does the same for the calendar exchange. When the run is given an explicit `Settings` (tests, a worker with overrides), Start's basis check and the per-intent permission check can apply different freshness limits.

**Fix:** Thread `settings` into `load_basis_verification_rows(session, *, settings, ...)` and use `settings.execution.account_snapshot_max_age_seconds`.

### WR-06: A future-dated account snapshot always reads as fresh and hides newer snapshots

**Files:** `src/trading_platform/services/portfolio.py:285-287` (`max((reference_now - snapshot_at).total_seconds(), 0.0)`), `src/trading_platform/services/account_baseline.py:27-32` (latest by `snapshot_at desc`)

**Issue:** `snapshot_at` is stamped by the host that ran the sync (`clock.now_utc()`, `sync_orders.py:96`, `:211`). The age is judged on the executor host, starting from the permission check's `at`, which is captured before the price GET. A negative age is clamped to 0, so a snapshot stamped ahead of the judging clock is always fresh. Because selection orders by `snapshot_at`, it also outranks snapshots written later with a correct clock until real time passes it. Worst case, the effective freshness bound becomes `max_age + skew`, and a wrongly dated snapshot's cash is used ahead of a newer correct one. It needs clock skew between the API and worker hosts, so the likelihood is low. The SAF-09 contract is a hard age bound.

**Fix:** Treat `snapshot_at > now + small_skew` as `account_snapshot_stale` (or `invalid`) instead of clamping. Consider ordering by `created_at` (DB clock), using `snapshot_at` only as the age input.

### WR-07: 0028 does not cover TRUNCATE, and evidence for legacy zero-attempt orders is not protected

**Files:** `alembic/versions/0028_phase20_1_attempt_log_append_only.py:68`, `:104-108`; `src/trading_platform/db/models/execution_operation.py:221` (intent `paper_order_id ON DELETE SET NULL`)

**Issue:** The trigger is `BEFORE UPDATE OR DELETE ... FOR EACH ROW`. Row-level triggers and FK `RESTRICT` do not fire on `TRUNCATE`, so `TRUNCATE order_submission_attempts` or `TRUNCATE paper_orders CASCADE` by the owning role still erases all attempt evidence. Through the intent `SET NULL` link, that makes intents look planned and re-sendable.

Separately, `RESTRICT` protects only orders that HAVE attempt rows. A legacy zero-attempt order (the TL-4 UNESTABLISHED shape) can still be deleted outright: it has no attempt evidence, and its order row is the only evidence there is. Deleting it removes the block, and any intent linked to it goes back to `planned`.

No production delete or TRUNCATE path exists in `src`, so this is hardening of the same class as SAF-10. The test suite does not use TRUNCATE (I grepped `tests/`), so a statement-level guard would not break the harness.

**Fix:**
- Add `CREATE TRIGGER ... BEFORE TRUNCATE ON order_submission_attempts FOR EACH STATEMENT EXECUTE FUNCTION ...` that raises, plus the same on `paper_orders`, or revoke TRUNCATE from the application role.
- Consider a `BEFORE DELETE` guard on `paper_orders` for rows that have no broker evidence (no broker id, status `pending_submission`/`submission_failed`/`unknown`).

### WR-08: The `retry_existing` guard still uses `classify_submission` and disagrees with the shared verdict on a REJECTED history

**Files:** `src/trading_platform/services/execution/submit_orders.py:2384-2405` (guard), `:2346` (identity assertion before it); `operations.py:1711-1716` (T1 `INTENT_NOT_SENDABLE`)

**Issue:** The `retry_existing` guard classifies with `classify_submission`, so any class other than `NOT_SENT` parks the order UNKNOWN and raises `AmbiguousOrderSubmissionError`, which flags the Job.

For a `pending_submission` order whose history is a recorded 4xx (the `reject()` persist lost the fence), the shared classifier says `REJECTED` (established, no gate). The guard instead manufactures an UNKNOWN order and a flagged Job, which then needs a fresh clean reconciliation. T1 also refuses this shape as `INTENT_NOT_SENDABLE`, which pauses `outcome_unresolved` while the gate reports no unresolved outcome. Both fail closed, but they disagree with the one verdict, which plan 17 claims every consumer reads.

Also, `_assert_pinned_identity` runs before this guard. An identity drift on an order with an ambiguous history therefore goes to `requires_reevaluation` without the order being parked UNKNOWN. The order stays visible to the gate through the unflagged branch, so it is safe, but the order state is less explicit.

**Fix:** Switch the guard to `classify_submission_evidence`:
- Park UNKNOWN only for `UNESTABLISHED`.
- Move `REJECTED` to `BROKER_REJECTED` (or `reuse_existing`).
- Keep `PROVEN_NOT_SENT` retryable.

Optionally, run the history guard before `_assert_pinned_identity`, so an unclean history is always parked first.

## Checked and sound (not findings)

- **T1 lock order:** the operation row `FOR UPDATE`, then the order row `FOR UPDATE`. The gate read (`load_trading_gate_state`) and the calendar read have no locking clause, so they cannot invert the singleton-first order used by handover and `_prepare_start`. `ControlStateUnavailableError` inside T1 escapes as a non-refusal. On the first attempt it leaves zero attempt rows, which is proven not sent; on a retry it leaves a complete `pre_connection` history. Both are consistent.
- **Retry refusal propagation:** `GuardedAttemptLog.begin_attempt` raises `SendRefusedError` from `alpaca.py:618`, before the transport `try`. `_send_authorized` re-raises it at `:2881-2888`, and `_execute_pinned_intent` maps it at `:2552-2573`. The order stays `pending_submission` with a complete `pre_connection` history.
- **Unflagged predicate branch:** a paused operation's registered-unsent intent is dropped, because it is `PROVEN_NOT_SENT`. Orders in the DB-06 accepted-without-id shape and NULL-attempt orders are now listed, which closes the KNOWN-1 gap.
- **attempt_log_registered inputs:** `operations._earliest_intent_created_at`, the predicate's `min(oi.created_at)` and `load_strategy_order_facts` give the same answer when the current intent references the order.
- **0028 shapes:** the jsonb-diff trigger leaves both completion writers legal. `updated_at` (`onupdate=now()`) is on the allow-list for shape (A). FK `SET NULL` on `strategy_run_id` touches no other column.
- **SAF-05 fragment:** `job_alias` is validated as an identifier, so the f-string interpolation cannot be injected. The operation id is compared as text, so a malformed payload cannot raise a cast error.
