## Narrative Findings (AI reviewer)

### Q1. The suppression cannot hide broker activity or release unresolved evidence

**The suppression only applies to local orders the broker did not return.**
- `_match_orders` resolves every broker order first, by `client_order_id`, then by `broker_order_id` (`matcher.py:228-245`).
- A matched local order is added to `matched_client_order_ids` (`:237`). From then on it can only produce STATE_MISMATCH (`:241-245`).
- `_is_local_order_active` (`:287-291`) is consulted only in the local-side loop, for orders no broker order matched (`:247-253`).
- MISSING_LOCAL for unmatched broker orders (`:233-235`), fills (`:258-284`) and positions (`:151-204`) are untouched.

**Attribution cannot remove the broker counterpart of a pre-send order.**
- An owned broker order is attributed through the local record that has its `client_order_id`, which belongs to the order's own strategy (`attribution.py:358-377`).
- `excluded_order_ids_for` therefore never removes it from that strategy's matcher input (`attribution.py:167-187`).
- In the account pass, only verified recorded-external orders are removed (`account.py:364-371`). A broker order matched by `client_order_id` can never be RECORDED_EXTERNAL: that is the `elif` at `attribution.py:378`.

**The explained set is closed, and everything else fails closed.**
- The explained set is exactly `{PROVEN_NOT_SENT, REJECTED}` (`matcher.py:77-79`).
- NOT_COMPUTED is the default (`snapshot.py:109`) and is also what `_local_evidence` returns for an order with no verdict (`report.py:668-676`). Both are reported.
- The mirror enum is a plain `enum.Enum`, so a stray string can never compare equal to it.

**Shape by shape:**

| Shape | How the verdict is reached | Result |
|---|---|---|
| Pre-send order carrying a broker id | BROKER_EVIDENCE (`attempts.py:303-304`) | reported |
| Ambiguous or unfinished attempt before or after a rejection | `classify_submission` lets AMBIGUOUS dominate (`:176-177`), giving UNESTABLISHED (`:313`) | reported |
| Legacy order that a later operation references | `attempt_log_registered` is False (`:272-276`) and there are zero attempts, giving UNESTABLISHED (`:319`) | reported |

**Compared with the old count rule:**
- **Newly suppressed:** only `pending_submission` orders with `submission_attempt_count >= 1` whose verdict is PROVEN_NOT_SENT or REJECTED.
- **Newly reported:** every `submission_failed` order and every zero-count pending order whose verdict is UNESTABLISHED or BROKER_EVIDENCE.
- **Unchanged:** `unknown` and terminal statuses are never reported.
- The suppression never exceeds what recovery already releases. Both read the same classifier (`recovery.py:508-517`).
- No resend path opened: Continue skips rejected intents, TL-10 refuses a new candidate, and `register()` applies the rejection without a POST. The 20.1-34 tests pin this.

**Other blocking mechanisms are unchanged.**
- `_evaluate_threshold_breach` (`report.py:800-846`) still blocks a `submission_failed` order at or above the threshold, whatever its verdict. This is fail-closed and outside D-G1-A.
- The broker is read before the local orders (`report.py:351-356`, `account.py:141-145`). An order registered concurrently is therefore judged against a broker snapshot that predates it. A reconciliation that overlaps a session stops qualifying through the effect boundary (`latest_broker_effect_at`). This design is unchanged.

**The json-to-jsonb comparison is sound.** jsonb equality is semantic: key order, whitespace, escape forms and numeric scale do not matter. Both kinds of json reader, the SQL `->` / `->>` operators and Python `json.loads`, take the last duplicate key, as jsonb does. So a rewrite that is jsonb-equal cannot change anything a gate reads. SQL NULL and JSON `null` compare as distinct, so that change is refused.

**Every legitimate writer passes:**
- **`_update_reconciliation_run` (`report.py:973-1006`) and `_finalize_run` (`account.py:475-507`):** the old row is pending, so no freeze applies. The ORM's SET list contains no link column, so guard 1 never fires.
- **`reclaim_stale_runs`:** touches `paper_execution` runs only (`stale_runs.py:61-69`), so guard 2 is never armed.
- **Job lifecycle writes:** none of them writes `job_type`, and the trigger is column-scoped with a WHEN clause.
- **Account `job_id` updates and their SET NULL:** guard 3 does not compare `job_id`.
- **SET NULL on a non-evidence run:** guard 1's predicate is false, so it passes.

**Product paths that now fail closed unexpectedly:**
- **A second completion write.** This happens only when the success write's COMMIT acknowledgement is lost, or when a database client completed the row first. See IN-01.
- **A retry of the completion writers.** There is none. `session_scope` commits exactly once (`db/session.py:96-105`), nothing wraps the writers in a retry, and a re-run Job creates a new run.
- **U+0000 in json.** Confirmed: E7 raises SQLSTATE 22P05 for any UPDATE of a completed account run whose json contains `\u0000`.
  - The only such UPDATE the product could cause is the `job_id` SET NULL of a Job delete. `src` and `scripts` contain no delete path (`DELETE FROM|session.delete(|delete(Job)`: no hit).
  - For strategy reconciliation runs, guard 1 already refuses that SET NULL.
  - So there is no product path. This was already recorded in 20.1-33-SUMMARY and is not re-reported.

**The downgrade is exact.** It drops the 4 triggers and 4 functions, in reverse order, with `IF EXISTS` (`:264-280`). The upgrade creates nothing else.

## Warnings

### WR-01: The job_type guard checks for a linked run only at UPDATE time, so a newer dirty strategy reconciliation can still be disqualified through its Job's type, and the guard then locks in the wrong type

**Files:**
- `alembic/versions/0030_phase20_1_evidence_update_guards.py:234-261`. The guard's only protection is the EXISTS lookup on `strategy_runs` at `:239-244`.
- `src/trading_platform/services/reconciliation/report.py:351-367`. The broker read runs BEFORE `_create_reconciliation_run` inserts and commits the run in its own transaction (`:941-970`); see also `jobs/handlers/reconciliation.py:72-78`.
- Gate readers: `latest.py:192-199` (`Job.job_type == RECONCILIATION_JOB_TYPE` at `:197`) and `recovery.py:711-716`.

**Issue.** The approved property: the `job_type` of the Job behind a standalone reconciliation never changes, in either direction (`0030:42-50`, the `Job` docstring). Guard 4 enforces it only when two conditions hold:
- the Job's `strategy_runs` row is committed and visible to the UPDATE's snapshot; and
- the name `strategy_runs` resolves to the real table.

There are three ways around it, each reproduced above:

1. **Pre-run window (E3).** A RUNNING reconciliation Job has no run row during the whole broker read. `UPDATE jobs SET job_type = 'paper_session' WHERE id = :job` passes. The handler then inserts the run with `trigger_source='job'`; nothing guards the INSERT.
2. **Insert race (E4).** The run INSERT's foreign key takes a `FOR KEY SHARE` lock on the Job row. An UPDATE of the non-key `job_type` column takes `FOR NO KEY UPDATE`, which does not conflict with it. Under READ COMMITTED, the EXISTS does not see the uncommitted run.
3. **TEMP shadow (E2).** The function is SECURITY INVOKER without `SET search_path`, and `pg_temp` is searched first for relation names. Any role with CONNECT and the default TEMPORARY privilege can bypass the guard at any time, even after the run is committed. The remedy documented for r3 IN-02 (separating the runtime and migration roles) does not remove that privilege.

**Effect.**
- The newer dirty run drops out of the strategy half of the gate, and the gate falls back to the older qualifying run. This is the scenario 0030 was approved to close.
- Once the run is committed, guard 4 refuses the converse UPDATE. Restoring `job_type = 'reconciliation'` therefore requires disabling the trigger.
- This is not product-reachable: no writer changes `jobs.job_type`.
- It gives no capability beyond the OPEN forged-INSERT item. But a guard the user approved does not deliver its stated property.

**Fix.** Keep the current lookup and add column-only arms, so the new guard is strictly stronger than the approved one:
- The `'reconciliation'` arms read no table, which closes ways 1 and 2 for the standalone Job.
- The pinned `search_path` plus the schema-qualified lookup close way 3.
- The EXISTS arm keeps today's protection for a Job of any other type behind a `'job'` run (for example a seeded `phase-probe` Job) in both directions.

No product writer changes `job_type` (20.1-33 inventory). The new arms widen the approved scope to every Job whose type is or becomes `reconciliation`, including queued and account-scope Jobs, so the change needs the user's approval.

```sql
CREATE OR REPLACE FUNCTION phase20_1_reconciliation_job_type_immutable() RETURNS trigger AS $$
BEGIN
    IF OLD.job_type = 'reconciliation'
       OR NEW.job_type = 'reconciliation'
       OR EXISTS (
           SELECT 1 FROM public.strategy_runs sr
           WHERE sr.job_id = OLD.id
             AND sr.run_type::text = 'reconciliation'
             AND sr.trigger_source = 'job'
       ) THEN
        RAISE EXCEPTION 'job_type of a reconciliation Job or of a Job behind a standalone reconciliation run is immutable'
            USING ERRCODE = 'integrity_constraint_violation';
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql SET search_path = pg_catalog, public;
-- The trigger definition stays as in 0030:
-- BEFORE UPDATE OF job_type ON jobs FOR EACH ROW WHEN (OLD.job_type IS DISTINCT FROM NEW.job_type)
```

**Where to put it.** Either a new revision, or an amendment of 0030 while it has run only on throwaway databases (Phase 21's 0031 chains on 0030).
- A new revision cannot use a bare `CREATE OR REPLACE` downgrade. Its downgrade must restore the original 0030 function body verbatim, so that a downgrade to 0030 reproduces 0030 exactly.
- Existing pins in `tests/test_phase20_1_evidence_update_guards_migration.py` must be reviewed:
  - the trigger-definition pin (`:439-453`; it still holds if the WHEN clause is unchanged);
  - the `'job'` literal pin (`:456-464`; it reads the 0030 source, so it needs a twin for a new revision);
  - the guard-4 lifecycle and mutation pins (test 12, and any pin that converts a Job INTO `reconciliation` and expects success).
- Pin the new `'reconciliation'` literal against `broker_jobs.RECONCILIATION_JOB_TYPE` (`broker_jobs.py:18`), the same way `'job'` is pinned against `STANDALONE_TRIGGER_SOURCE`.

**Alternative**, if the scope must not widen:
- a `BEFORE INSERT` guard on `strategy_runs` that refuses a `reconciliation` / `'job'` run unless `(SELECT job_type FROM public.jobs WHERE id = NEW.job_id FOR SHARE) = 'reconciliation'`. This closes ways 1 and 2: the lock serialises the race, and the INSERT fails instead of linking to a retyped Job.
- plus `SET search_path` on both functions, which closes way 3.

**Add pins for:**
- the pre-run window (a RUNNING reconciliation Job with no run);
- a concurrent UPDATE racing the run INSERT;
- a TEMP `strategy_runs` table in the session.

### IN-01: The completion writers assume the run is still pending. Under complete-once, a run that is already completed makes the genuine completion fail and hides the original error; in the forged case the genuine result is never stored

**Files:**
- `report.py:399-443`: the success write is in the `try`. The failure write, then `logger.exception` and `raise`, are in the `except`.
- `report.py:973-1006`: writes without checking the current status.
- `account.py:131-148`: the pending row is committed BEFORE the broker read.
- `account.py:208-248` and `:475-507`.
- `0030:149-161` and `:194-213`.

**Issue.** Complete-once means the first completion write wins. Two shapes reach the `except` branch with the row already completed:

- **(a) Lost COMMIT acknowledgement.** The success write commits on the server, but the client receives an error.
  - The failure write is then refused with "... is complete-once ...".
  - That IntegrityError is raised inside the `except` block, so `logger.exception` (`report.py:432-442`, `account.py:238-247`) never runs. The original error is replaced, and the Job fails with a misleading message.
  - The stored run is the genuine success. Before 0030, it was overwritten with FAILED.
- **(b) A database client completes the pending run first.**
  - An account run is pending for the whole broker read. During that window, `UPDATE account_reconciliation_runs SET status='succeeded', completed_at=now(), blocks_execution=false, unresolved_reasons='[]', classification_summary='{"orders":{"unrecognized":0},"fills":{"unrecognized":0}}', result_summary='{"non_terminal_order_count":0}', unexplained_exposure='{}' WHERE status='pending'` passes guard 3.
  - The genuine finalize write is then refused, and so is the failure write.
  - The forged clean row is frozen. It is the newest completed run, and A2-A4, A6 and the account half of the gate read it.
  - The genuine and possibly dirty summary is stored nowhere. Before 0030, the genuine write overwrote the forgery.
  - This is the same class as the OPEN forged INSERT, but round 3 changed it, and it now destroys genuine evidence instead of adding a row.

**Fix.**
- In both writers, lock the row (`with_for_update`) and check `status == pending and completed_at is None` before writing.
- If the check fails, emit a structured log carrying the genuine summary and the stored status, then raise a typed error.
- In both `except` branches, log first. Treat a refused failure write as "already completed", and re-raise the ORIGINAL exception.
- List "out-of-band completion of a pending run" with the OPEN forged-INSERT item.

### IN-02: The inputs to the G-1 verdict are still UPDATE-able, and one UPDATE now makes the reconciliation and A6 report clean as well as releasing the gate

**Files:**
- `attempts.py:416-433`: the provenance check compares `min(execution_operation_intents.created_at)` with `paper_orders.created_at`.
- `attempts.py:302-319`: the verdict also reads the order's status and broker id.
- Existing protection: 0028 (attempt rows), and 0029 `:110-131` (only `paper_orders.strategy_run_id`). Intents are guarded against DELETE and TRUNCATE only.

**Issue.** Apart from the attempt log, the verdict's inputs are plain data. One UPDATE turns a legacy zero-attempt order from UNESTABLISHED into PROVEN_NOT_SENT. Any of these works:
- back-date the earliest intent row that references the order;
- point an old intent's `paper_order_id` at the order;
- move the order's `created_at` after its first intent.

Recovery, T1 and the `register()` guard already read the same inputs. The old count rule could be flipped just as easily through `paper_orders.submission_attempt_count`. So the capability is not new. But round 3 extends the reach of that UPDATE to every reconciliation pass, and therefore to A6 (whether an account M5 is clean). This is outside the approved WR-01 scope.

**Fix.** User decision, as part of the same-class OPEN list. Candidate guards, after a 20.1-33-style sweep for writers:
- `execution_operation_intents.created_at` immutable;
- `execution_operation_intents.paper_order_id` immutable once non-NULL (binding NULL to a value stays legal);
- `paper_orders.created_at` immutable.

### IN-03: The 0029 and 0030 guard functions look up table names through the caller's search_path

**Files:** `0030:111-115` (guard 1's EXISTS arms), `0030:239-244` (guard 4, see WR-01), `0029:171-183` (the R and J EXISTS arms).

**Issue.** A session-level TEMP table named `paper_orders`, `order_events`, `order_submission_attempts` or `strategy_runs` shadows the real table inside these EXISTS checks (E2, E5).

Today the `run_type` / `job_type` / `outcome_uncertain` arms read no table and still protect every evidence row the product creates:
- E6 shows a `paper_execution` run still refusing with all three shadows present.
- A shadowed 0029 J check on a Job behind a reconciliation run still aborts at 0030's SET NULL check.

So the only exposure is untyped runs referenced by orders, events or attempts, which is not a product shape, plus guard 4 (WR-01). It matters for r3 IN-02, because separating the roles leaves the PUBLIC TEMPORARY privilege in place.

**Fix.**
- Run `ALTER FUNCTION <each 0029/0030 guard function>() SET search_path = pg_catalog, public;`, or schema-qualify every table name, in the next revision.
- Add `REVOKE TEMPORARY ON DATABASE <db> FROM PUBLIC` to the r3 IN-02 role-separation work.
