## The appended runbook note (runbook 05, after the 2026-10-05 CR-01 note; one line, quoted in full)

> **Note (2026-10-06, gap round 3, plans 20.1-32..36 - PENDING VERIFICATION; the interim prohibition above remains in force and is not lifted by this note):** (1) G-1, the decided rule (D-G1-A, user decision 2026-10-06): a reconciliation (M5, and the check inside a session start) decides whether a locally registered order the broker does not show is a problem with the same proof as the recovery gate. An order in `pending_submission` or `submission_failed` is NOT reported missing at the broker when that proof says (a) no request ever left the process (an operation-bound order that never got an attempt row, or whose every attempt failed before connecting or expired before sending), or (b) the broker definitively rejected it: every attempt finished and at least one was a 4xx rejection, with no unfinished, ambiguous, duplicate-reported or accepted attempt before or after it. The attempt counter on the order is not proof. A definitively rejected order is never sent again: Continue skips it and a new session in the same evaluation session refuses it (`replay_of_earlier_decision` / `action_already_submitted`, TL-10). (2) Behaviour change: every other order in those two states IS reported `MISSING_BROKER` in every reconciliation that loads it: a legacy order from before the attempt log, an order whose attempt has no outcome or an ambiguous one (also when a rejection comes before or after it), a duplicate-reported or accepted-without-broker-id attempt, and a pre-send order that carries a broker id the broker does not return. Before this change `submission_failed` and zero-count pending orders were never reported. (3) Consequences: an account reconciliation (M5, account scope) reads every order of every strategy for all time, so one such order anywhere that the broker does not return makes every account M5 not clean. A6 (seeding, handover, release) needs a clean ACCOUNT M5 and therefore refuses while such an order exists, whichever strategy holds it; an owner-scope M5 never satisfies A6. For a legacy or unproven order without a broker id A5 already refuses on the same order (TL-4); for a pre-send order with a broker id the broker does not show, A6 is a new refusal while A5 may pass. Account-level uncertain Jobs (such as the 29 Sep `broker-order-sync` Job) can be cleared only by a clean account M5, so they stay unresolved while such an order exists. Owner trading: trading blockers, the per-intent permission check, Continue (M11) and the evaluation basis use the newest standalone M5 of either scope after the owner's latest broker effect, so a not-clean account M5 caused by ANOTHER strategy's order pauses the owner until a newer clean owner-scope M5 (`{strategy_id, as_of_session}`) completes, and the next account M5, including the one record-external-activity runs, makes it not clean again. A1, A2, A3, A4 and A7 are unchanged. (4) Permission is not resolution: a clean owner-scope M5 restores the current owner's permission to trade only; it does not resolve another strategy's uncertainty, does not change any classification and does not satisfy A5 or A6; that strategy stays blocked until the broker shows its order or its attempt history proves it (TL-4), and ownership cannot change meanwhile. (5) Before any real-stack UAT, the read-only inventory of non-terminal dev-database orders (HUMAN-UAT Step 0) is MANDATORY: any listed order stops the UAT for the user's review; a listed order is a review item, not a finding or an outcome classification, and the inventory never authorizes an edit, delete, cancel, override or resubmission of any order. (6) An order the broker does return is never hidden by this rule, and unrecognized broker activity still blocks; Continue (M11) still requires a fresh clean standalone M5 and does not run one itself. (7) From migration 0030 the database also refuses UPDATEs that would detach an execution or reconciliation run from its Job, change its type or its strategy, change the type of the Job behind a standalone reconciliation, or rewrite a completed reconciliation result (retention / evidence policy, user decisions 2026-10-06); the table-owning database role can still bypass triggers (documented limit, IN-02). (8) Unchanged: genuinely ambiguous attempts stay `outcome_unresolved`; a Job that created a run but registered no order stays `execution_path_unproven` (OD-1 OPEN); R3 is read-only evidence; End + M5 is not a release; no database edit, override or resubmission is ever part of a procedure. (9) Lifting the prohibition requires the verification of these plans AND an explicit user decision.

> ### Step 0 (MANDATORY before procedure 1): read-only inventory of non-terminal orders
>
> Decision D-G1-A (user, 2026-10-06) makes this step mandatory before any real-stack UAT: it is read-only, it contacts no broker, it runs BEFORE the Alembic upgrade that brings the database to the head named in the preconditions (the query works at revision 0021 and at head), and no listed order is ever edited, deleted, cancelled, resubmitted or overridden.
>
> 1. Record the database revision (read-only): `PYTHONPATH=src .venv/bin/alembic current`.
> 2. Run the query below in a read-only session, for example `PGOPTIONS='-c default_transaction_read_only=on' psql "<dev database URL>" -v ON_ERROR_STOP=1 -f <file holding the query>`. The query sits between the two marker comment lines below (the start marker above the fence, the end marker under it) and is exactly:
>
> ```sql
> SELECT s.strategy_id AS strategy, po.id AS paper_order_id, po.client_order_id,
>        po.status::text AS status, po.broker_order_id, po.submission_attempt_count,
>        po.created_at, sr.run_type::text AS origin_run_type, sr.job_id AS origin_job_id
>   FROM paper_orders po
>   JOIN strategy_runs sr ON sr.id = po.strategy_run_id
>   JOIN strategies s ON s.id = sr.strategy_id
>  WHERE po.status::text IN ('pending_submission', 'submission_failed', 'submitted',
>                            'partially_filled', 'unknown')
>  ORDER BY po.created_at, po.id;
> ```
>
> 3. How to read each row. A row is a REVIEW ITEM, not a verdict: the inventory itself produces no reconciliation finding and no outcome classification; after the upgrade those come only from the product (M5 findings, the recovery classification) and depend on what the broker returns. A listed row therefore does not by itself make a clean account M5 impossible; it is the reason for the review. By status:
>    - `pending_submission` / `submission_failed` without a broker id: at revision 0021 the attempt log (0023) and operation intents (0027) do not exist, so the order is a legacy order; after the upgrade its shared verdict is `unestablished` (TL-4): the recovery classification blocks its strategy (`outcome_unresolved`) and A5, and while the broker does not return its client_order_id every reconciliation that loads it (its strategy's M5 and every account M5) reports it `MISSING_BROKER`, so no account M5 is clean (A6 refuses every ownership change; account-level uncertain Jobs such as the 29 Sep `broker-order-sync` Job stay unresolved; an owner's sends pause while such an account M5 is its newest standalone reconciliation).
>    - `pending_submission` / `submission_failed` with a broker id: the verdict is `broker_evidence`; the order is reported `MISSING_BROKER` only if the broker does not return that id (then the same account-wide effect, while A5 may pass); if the broker returns it, the reconciliation compares the states.
>    - `submitted` / `partially_filled`: a known active order, compared with the broker as before G-1; if the broker returns it in the expected state there is no finding, and only a broker account that does not know it reports `MISSING_BROKER`.
>    - `unknown`: the recovery classification blocks its strategy and A5 (`outcome_unresolved`, TL-4); it never produces a `MISSING_BROKER` finding.
> 4. The STOP rule (a conservative review stop): if the query returns ANY row, stop before procedure 1 and send the result and the revision of item 1 to the user; the UAT continues only after the user's explicit decision; with no row, continue. The stop is a review gate, distinct from a reconciliation finding and from an unresolved-outcome classification; inventory results never authorize an edit, delete, cancel, override or resubmission of any order.
