# Phase 20.1: Focused Safety Review

**Reviewed:** 2026-10-05
**Scope:** focused-safety, six areas (see frontmatter), implementation and tests
**Status:** issues_found

## Summary

The submission-safety core is, on the code paths read, sound: every POST goes through one site (`alpaca.py:608`), `begin_attempt` fails closed outside T1, T1 locks the operation row then the order row and requires `proven_not_sent`, every in-loop retry runs its own T1, takeover is a two-transaction epoch-then-read, End/expiry only move proven-not-sent intents, and there is no broker cancel/DELETE/PATCH path anywhere in `src`. No finding allows a duplicate or re-sent order on an ambiguous outcome.

The defects are on the edges of that core: (a) the recovery predicate and the run-time send guard disagree about what a registered-but-never-attempted order is, in the fail-closed direction (permanent block with no release path, SAF-01); (b) T1 re-authorizes each HTTP attempt without re-running any permission step, so kill switch, enabled status and window are checked once per intent, not per attempt (SAF-02); (c) Continue does not assert that the identity it sends equals the pinned identity (SAF-03); and (d) several fail-closed deadlocks and over-blocking paths.

Findings KNOWN-1 .. KNOWN-5 are referenced, not re-reported. SAF-01 deepens KNOWN-1 from the opposite side. SAF-08 interacts with KNOWN-2.

## Findings

### SAF-01 (high, area 4): recovery classification never accepts the attempt-log proof; a provably-unsent operation-bound order blocks the strategy and ownership changes permanently

- **File:** `src/trading_platform/services/recovery.py:440-485` (`classify_intent`, zero-attempt branch at 476-481), `:558-608` (`_INTENTS_SQL`), `:885-976` (`_evaluate`); contrast `src/trading_platform/services/execution/attempts.py:253-282` (`proven_not_sent`), `operations.py:728-762` (`_attempt_log_registered`), `submit_orders.py:1777-1785` (`local_unestablished`), `intent_identity.py:274-290` (`verify_evaluation_basis`, "gate-neutral" legacy marker).
- **Defect:** The run-time side treats an operation-bound order with zero attempt rows (and status `pending_submission`) as PROVEN NOT SENT (CONTEXT S1-R3 / 04 line ~745; `authorize_send` will send it). `classify_intent` never consults that proof: `if attempts:` is the only path to `not_sent`, so zero attempts falls through to `NOT_FOUND`, which is `blocking`. `strategy_recovery_status` accepts an `operation_view` argument and never uses it (`recovery.py:140-147` states "the predicate itself never reads it"). The docstring ("without an operation (20.1-11) an order cannot prove it was registered under the attempt-log invariant") predates 20.1-11 and was not updated. Absence evidence, End, expiry and elapsed time can never release a NOT_FOUND order (TL-4 / round 5).
- **Failure scenario A (lease loss / crash):** executor registers intent 2 (`register()` commits: order `pending_submission`, zero attempts, linked to the operation intent), then the worker is killed or its lease lapses before or inside T1 (`LEASE_LOST` refusal). The sweep marks the Job FAILED with forced `outcome_uncertain=True` (`jobs/lifecycle.py:72-78`). The order is linked through `strategy_runs.job_id`, is classified `NOT_FOUND`, and `_evaluate` returns `OUTCOME_UNRESOLVED`. Continue is refused at submit (`_require_recovery_resolved`), A5 fails (`UNRESOLVED_OUTCOME`), the strategy cannot start a new session, and ownership cannot change. End terminates the operation, but the order stays `pending_submission` with a flagged Job forever. `proven_not_sent` says it was never sent; the predicate says it is unresolved; nothing can reconcile the two.
- **Failure scenario B (exception in T1):** `authorize_send` raising anything other than `SendRefusedError` (DB serialization or connection error) lands in the generic `except Exception` branch (`submit_orders.py:2543-2562`): the order becomes `submission_failed` with zero attempts and the Job fails with `external_*` logged, so it is flagged. Same permanent block; `_prepare_start`'s `local_unestablished` and `verify_evaluation_basis` deliberately treat this exact shape as gate-neutral, so three of four consumers say "never sent" and the one that gates ownership says "unresolved".
- **Confidence:** confirmed by code path. The trigger frequency (crash or lease loss in the window between the registration commit and T1's commit, or a non-refusal error inside T1) is low, the consequence (needs DB surgery) is not.
- **Deepens KNOWN-1 (other direction):** KNOWN-1 is the predicate being narrower than the run-time check. This is the predicate being wider than the run-time proof. Both come from `_INTENTS_SQL` / `classify_intent` not sharing `proven_not_sent`. Related under KNOWN-1: the unflagged branch of `_INTENTS_SQL` (`recovery.py:589-599`) covers only `unknown` and `pending_submission`-with-a-NULL-attempt, so `submission_failed` with a NULL or ambiguous or accepted attempt (see SAF-06) is visible only through a flagged Job.
- **Fix direction:** have the predicate classify through one shared function with the run-time guard (`attempts.proven_not_sent` plus `_attempt_log_registered`), so an operation-bound zero-attempt `pending_submission`/`submission_failed` order is `not_sent`; leave legacy zero-attempt orders unproven. Make the same shared function drive the unflagged branch so both KNOWN-1 and this finding close together.
- **Missing test:** `tests/test_recovery_predicate.py:526-552` pins only the LEGACY (non-operation) zero-attempt case (`NOT_FOUND`) and the unflagged-plain case. No test links an operation intent to a zero-attempt `pending_submission`/`submission_failed` order on a FLAGGED Job and asserts the gate, A5, and the Continue submit gate agree with `authorize_send`.

### SAF-02 (medium, areas 1 and 3): T1 and the in-loop retries re-authorize without re-running kill switch, enabled, window, or price checks

- **File:** `operations.py:1601-1737` (`authorize_send`; no kill-switch, enabled, owner or window read), `send_guard.py:126-141` (`begin_attempt` retry runs a bare `authorize_send`), `alpaca.py:583-640` (retry loop with `time.sleep`), `core/settings.py:201-203` (`max_retries=3`, `timeout_seconds=30.0`), `permission.py:452-545` (the single check), `permission.py:318` (`age` against `now` captured at line 452).
- **Defect:** The fixed-precedence permission check (module docstring: "run before EVERY broker action") runs once per intent, before the price GET, the manifest verification, the portfolio load, the registration transaction and T1. T1 re-verifies fence, lease, intent sendability and the recovery predicate only. A `pre_connection` failure (ConnectTimeout is 30 s by default) is retried up to 3 more times, each re-authorized by T1 alone, after `time.sleep` backoff. CONTEXT D-03: "Ownership is re-checked immediately before every broker action"; S1-R3: T1 "before EVERY HTTP attempt".
- **Failure scenario:** operator trips the global kill switch, disables the strategy, or the execution cutoff passes while attempt 1 is connect-timing-out. Attempts 2-4 each pass T1 and POST; worst case about `4 x 30 s + 3.5 s` (about 2 minutes) after the last permission read. The same gap applies to the first attempt for the registration-to-T1 interval and, for ownership, is only masked because handover is blocked by A1 while a Job runs or an operation is open (so ownership is protected indirectly; kill switch, enabled and window are not).
- **Related (price age):** `price_step` computes `age = now - observation.observed_at` with `now` captured before the GET, the manifest verification and up to `3 x (30 s + backoff)` of GET retries (`alpaca.py:1010-1030`), so staleness is understated by the whole lookup duration and is never re-measured before the POST. A trade timestamp in the future also passes (`age` negative).
- **Confidence:** confirmed by code path. Severity is medium; it becomes high if the contract reading is "kill switch honoured immediately before each POST" (D-03 says that for ownership, the kill-switch wording in CONTEXT is only "paused: kill switch", not a timing rule).
- **Fix direction:** make T1 read the same gate statement used by `load_trading_gate_state` (kill switch, owner, enabled) and the window verdict in the same transaction as the operation row lock, and fail the refusal into the existing pause path; measure price age from `observation.fetched_at`/the current clock. Cheap, because T1 already opens a transaction and holds the operation row.
- **Missing test:** no test changes the kill switch, strategy status or window between a `pre_connection` failure and its retry (tests at `test_paper_session_operations.py:455`, `:3570` cover only pause-after-failure and takeover). No test asserts price age is judged against the fetch time.

### SAF-03 (medium, area 3): Continue never asserts that the sent identity equals the pinned identity

- **File:** `submit_orders.py:2108-2131` (`_candidate_for_view` re-derives symbol, side, quantity, price from the risk event), `:2189-2335` (`register` and `registration["client_order_id"]`), `:2220` (`_CONTINUATION_ACTIONS` checks only the action type), `:2388-2394` (`OrderIntent` built from `registration`, not from `view`); `execution/idempotency.py:104-138` (`client_order_id` is built from the settings `prefix`).
- **Defect:** The identity that is sent comes from `derive_order_identity(prefix=settings..., candidate=<rebuilt from RiskEvent>)` or from an existing order found by `intent_hash`; it is never compared with `view.client_order_id` / `view.quantity` of the pinned `execution_operation_intents` row. D-19/S2-R3 require "same intent, client_order_id, symbol, side, quantity and identity".
- **Failure scenario:** `execution.client_order_id_prefix` is changed (settings are not part of the strategy-settings manifest that triggers re-evaluation) between Start and Continue. For a planned, never-registered intent the decision is `create_new` (the `intent_hash` lookup excludes the prefix and finds nothing), the order is registered with the NEW prefix's `client_order_id`, `_link_intent` re-links the intent, and `_CONTINUATION_ACTIONS` accepts `create_new`. The order sent no longer carries the pinned client_order_id (and the operation row now disagrees with the broker). A mutated `proposed_quantity` on the risk event, or the `quantity <= 0` fallback in `_candidate_for_view`, change identity the same way (the fallback also substitutes `Decimal("0")` for a missing reference price).
- **Confidence:** plausible. The code path is confirmed; reaching it needs a settings change or a mutated risk event between the two runs.
- **Fix direction:** after the registration decision, assert `registration["client_order_id"] == view.client_order_id` and `quantity/side/symbol == view.*` (raise before T1, pause best-effort, send nothing); build `OrderIntent` from the pinned view.
- **Missing test:** no test changes the prefix (or the risk event) between a price pause and Continue and asserts "zero POST, identity unchanged".

### SAF-04 (medium, area 4): any flagged paper-session Job that created a run but no order blocks the strategy and the account permanently; Job-level records are write-only

- **File:** `recovery.py:777-806` (Job-level entries: `run_count > 0` and no orders is always `UNRESOLVED / EXECUTION_PATH_UNPROVEN`), `:1413-1478` (`assess_unestablished_intents` appends a Job-level classification that `_load_intents` never reads), `:1293+` (`record_broker_statement`).
- **Defect:** `outcome_uncertain` is forced on any handler error after the always-logged `external_broker_session_started` (`jobs/runner.py:339`, `handlers/paper_session.py:77`). A Job that fails after `_create_paper_execution_run` and before the first registration (unexpected exception, `ExecutorJobRequiredError`, a DB error in `_resolve_source_risk_run`, worker loss) has `run_count > 0` and zero orders, so it is classified `EXECUTION_PATH_UNPROVEN`. The classification ignores `job.records`, so no recorded evidence changes it, and a Job-level entry has no `intent_id`, so no statement can attach to it. This matches the spec text ("zero rows alone is not enough"), but nothing in the implemented surface can supply the "execution-path position of the failure" evidence the same spec requires to move it to `nothing_submitted`.
- **Failure scenario:** a transient failure before any order is registered: the strategy is permanently `outcome_unresolved`; `PUT active-paper-strategy` fails A5 for every handover/release; the only way out is manual DB edits.
- **Confidence:** confirmed by code path; the "no release" outcome is spec-conformant for TL-4 (ambiguous ORDER) but is not required by TL-4 for a Job that never registered an order.
- **Fix direction:** either classify a failed Job whose run left zero order rows and zero operation/intent rows through an evidence record the sync pass can write (error signature + call order), or document and test that this state is terminal.
- **Missing test:** `test_recovery_predicate.py:470` asserts the block but there is no test of a path to release, or of the intended operator runbook.

### SAF-05 (low, areas 2 and 4): Continue payloads carry no `strategy_id`, so flagged Continue Jobs and their effects count as account-level for every strategy

- **File:** `paper_session_submission.py:446` (payload `{mode, operation_id}`), `recovery.py:558-571` and `:610-622` (`j.payload ->> 'strategy_id'`), `reconciliation/latest.py:101-110`.
- **Defect:** every query keyed on `payload->>'strategy_id'` treats a Continue Job as account-level. Consequences: a flagged Continue Job (or one with `EXECUTION_PATH_UNPROVEN`) blocks every strategy and `account_recovery_status`'s `None` subject (A5); a completed Continue Job moves the effect boundary of every strategy and the A6 boundary, forcing an extra reconciliation. Muted by single ownership.
- **Confidence:** confirmed.
- **Fix direction:** stamp the operation's strategy on the Job at admission (the admission hook already resolves it) or join through `execution_operation_jobs`.
- **Missing test:** none covers a flagged Continue Job of strategy A against strategy B's gate.

### SAF-06 (low, area 1): an exception after the ACCEPTED outcome is recorded is treated as "no broker side effect is known"

- **File:** `submit_orders.py:2543-2562` (generic `except Exception`; `failure_error = exc` is also assigned twice at `:2544-2545`), `alpaca.py:292-311` (`_normalized_result` can raise `InvalidOperation`/`ValueError` on a 2xx body), `:741-776` (`_resolve_duplicate_reply` returns `_normalized_result` of the snapshot).
- **Defect:** the attempt row is already `accepted` (or `duplicate_reported`) when `_normalized_result` raises; the handler records `SUBMISSION_FAILED`, writes `broker_payload={"error": ...}`, schedules no reconciliation, and the comment says "no broker side effect is known". A broker-accepted order with no broker id is mislabelled a clean failure.
- **Why it is only low:** a resend is still blocked (`authorize_send` requires `proven_not_sent`; `classify_submission` is `accepted`; takeover's `_in_doubt` includes `accepted`), and the Job is flagged, so the predicate (through the Job) and `_prepare_start`'s `local_unestablished` still see it. It is visible only through the flagged Job, not through the unflagged `_INTENTS_SQL` branch (see SAF-01 / KNOWN-1).
- **Fix direction:** catch parse errors inside `submit_order` after recording the outcome and raise `AmbiguousOrderSubmissionError` (`reason="invalid_response_body"`) so the order is parked UNKNOWN and reconciliation is scheduled; delete the duplicated assignment.
- **Missing test:** none feeds a 2xx body that parses as a dict but fails `_normalized_result` (non-numeric `qty`, bad `submitted_at`).

### SAF-07 (low, areas 4 and 6): bulk sync and pre-lock recovery bind broker orders to local intents by client_order_id alone (D-07 not applied)

- **File:** `execution/sync_orders.py:311-345` (`_sync_paper_orders`, match at `:322-325`), `reconciliation/report.py:154-209` (`recover_inflight_paper_orders`, runs in `run_paper_session` before `session_run_lock` and outside any fence); contrast `alpaca.py:473-507` and `recovery.py:1387-1410` (full D-07 check: symbol, side, quantity, type, `created_at >= registered_at`).
- **Defect:** an UNKNOWN or ambiguous local order is bound to whatever broker order carries the same `client_order_id` (`local_order.broker_order_id = ...`, status transition), after which `classify_intent` returns `found_verified` (broker id present). The D-07 checks exist only for the duplicate-reply lookup and the recovery single-order lookup. A same-day deterministic id collision (re-created DB against a reused paper account) would mark an unresolved order verified.
- **Mitigation:** the next account reconciliation applies the stricter attribution classifier and reports a blocking anomaly, and `_evaluate` also needs a clean reconciliation after the effect, so the strategy stays blocked; the established intent classification itself is wrong for an interval.
- **Fix direction:** run the same `_lookup_mismatch` check in `_sync_paper_orders` / `_apply_broker_order_snapshot` before binding a broker id to a local order that has no broker id.
- **Missing test:** no test syncs a same-id, different-symbol/quantity/earlier-`created_at` broker order against an UNKNOWN local order and asserts it is not bound.

### SAF-08 (low, area 6; interacts with KNOWN-2): S3-R4(5) "exit quantity = the whole verified position" is not enforced

- **File:** `intent_identity.py:739-790` (`classify_candidate`, sell check at `:764` only tests `held <= 0`), `risk.py:542-580` (`revalidate_pinned_intent` refuses only `held < quantity`).
- **Defect:** a sell candidate smaller than the verified position is eligible and sendable, leaving a remainder that is not the TL-11 "partial-fill remainder"; a candidate larger than the position is caught only at the pre-send revalidation (`no_open_position`, a re-evaluation pause) rather than at intent creation. With KNOWN-2 (account-path sync never opens a Position) the `held` value comes from the `Position` table, which can lag the fill-derived position the basis was verified against (`verify_evaluation_basis` step (v) is skipped when the history is empty).
- **Fix direction:** add a disposition (e.g. `exit_quantity_mismatch`) in `classify_candidate` comparing `key.quantity` to the verified `held`.
- **Missing test:** none asserts a sell for `held - 1` or `held + 1` shares is refused at creation.

### SAF-09 (low, area 6): portfolio cash basis has no freshness bound, the configured-cash fallback is not gated, and snapshot ordering uses sync start time

- **File:** `portfolio.py:150-220` (`load_state_with_basis`; `age_seconds` is recorded, never enforced; fallback to `starting_cash` when no snapshot), `intent_identity.py:262-290` (`verify_evaluation_basis` returns verified for an empty history without checking `basis_source`), `sync_orders.py:79` and `:548` (`snapshot_at=synced_at`, stamped before the broker reads), `account_baseline.py:24-32` (latest by `snapshot_at`).
- **Defect:** (a) the per-intent risk check (`permission.py:537`) sizes against whatever the latest `broker_sync` snapshot says, however old; the only enforcement of "refreshed" is indirect (a working order forces a sync). (b) With no snapshot the basis is `configured_starting_cash` and verification passes. (c) Two overlapping syncs can leave an older observation with the later `snapshot_at`.
- **Fix direction:** reject (pause `awaiting_reconciliation` or re-evaluate) a basis older than a configured age or sourced from `configured_starting_cash` for execution; stamp `snapshot_at` after the account read.
- **Missing test:** no test exercises a stale-snapshot or fallback-source basis through the permission check.

### SAF-10 (low, area 1): attempt-log append-only and complete-once are code-only; the FK cascades evidence

- **File:** `alembic/versions/0023_phase20_1_order_submission_attempts.py:88` (`paper_order_id ... ondelete="CASCADE"`), `:22-34` (docstring: "append-only in code"), `attempts.py:458-481` (`_complete` guard under FOR UPDATE), `operations.py:1746-1840` (`complete_attempt_late`), `0027` (`execution_operation_intents.paper_order_id ondelete="SET NULL"`).
- **Defect:** no trigger or constraint prevents `UPDATE` of a completed attempt (outcome `ambiguous` rewritten to `pre_connection`) or `DELETE`; deleting a `paper_order` cascades its attempt evidence and nulls the intent link, which makes the intent look `planned` and re-sendable. No delete path exists in `src`, so this is a hardening gap, not a live bug; the safety property "never resend after ambiguity" rests entirely on application discipline.
- **Fix direction:** `BEFORE UPDATE OR DELETE` trigger on `order_submission_attempts` allowing only the single NULL-to-outcome completion; `RESTRICT` on the attempt FK.
- **Missing test:** the migration tests assert CHECKs and the unique key but not that a completed row cannot be rewritten.

### SAF-11 (low, area 2): dead fenced helpers that are not actually atomic

- **File:** `operations.py:1359-1411` (`cas_set_intent_disposition`, `cas_update_order`; no production caller, only exports and one test, `test_every_fenced_cas_helper_affects_zero_rows_when_stale`).
- **Defect:** the fence for these is an `EXISTS` subquery against a different table than the one updated; under READ COMMITTED the subquery uses the statement snapshot and takes no row lock, so a `terminate_operation` or `acquire_execution` that commits during the statement is not seen. The production path uses `_persist_fenced` (FOR SHARE on the operation row) and `cas_update_operation` (the fence is on the updated row, so Postgres re-evaluates it), which are correct. A future caller of these two helpers would get a non-atomic fence while the test suggests otherwise.
- **Fix direction:** delete them, or have them take `fence_held(..., lock=True)` first.

### SAF-12 (low, area 2): `session_run_lock` cleanup can skip `connection.close()`

- **File:** `services/concurrency_guard.py:117-120`.
- **Defect:** in `finally`, if `pg_advisory_unlock` raises, `connection.close()` is skipped and the exception replaces the original one. The session-level lock then lives until the pooled connection is recycled or dropped, blocking that `(strategy, session)` key (`operation_executor_active`). Requires a driver error on the unlock statement; usually a broken connection, which also releases the lock server-side.
- **Fix direction:** nest `try/finally` so `connection.close()` always runs; on unlock failure `connection.invalidate()`.

## Per-area notes

### Area 1: attempt logging, ambiguity, duplicate prevention

**Invariants checked and found sound**
- Single POST site: `alpaca.py:608`; `_request_with_retry` is GET-only (`alpaca.py:983-988` raises on non-GET); no other `.post(`, `.delete(`, `.patch(`, `.put(` against the broker in `src`.
- `begin_attempt` raises `AttemptNotAuthorizedError` outside T1 (`attempts.py:392-396`), and only `authorize_send` opens `send_authorization_scope` (`operations.py:1709`).
- T1 locks operation then order `FOR UPDATE`, checks state, epoch, executor, DB-clock lease, intent open/registered, `retryable and proven_not_sent`, and the recovery predicate, then inserts the NULL-outcome row and commits before the POST (`operations.py:1601-1737`).
- Every retry runs its own T1 (`send_guard.py:126-141`); the in-loop retry occurs only while every attempt so far is complete `pre_connection`/`deadline_expired` (`alpaca.py:567-575`, `:621-645`); any ambiguous outcome raises and is never re-sent.
- Classification is conservative: 429/5xx/1xx/3xx/read timeouts and every non-connect transport error are `ambiguous` (`attempts.py:128-146`); a 2xx without a JSON object is demoted to `ambiguous` (`alpaca.py:660-665`); an outcome that cannot be recorded raises `AmbiguousOrderSubmissionError` (`alpaca.py:697-739`).
- Duplicate reply triggers exactly one lookup with the D-07 identity check; a failed or mismatched lookup stays `exists_reported` (ambiguous) (`alpaca.py:741-776`).
- Wall-clock deadline re-read immediately before the HTTP hand-off and a deadline miss is recorded `deadline_expired` (`alpaca.py:583-604`, `send_guard.py:143-150`).
- Pre-lock reconciliation writes (`recover_inflight_paper_orders`, `apply_reconciliation_corrections`, `report.py:154-292`) apply broker evidence through legal transitions only and write `sync_failure_*` bookkeeping; they cannot un-park an ambiguous order or touch attempt rows (see SAF-07 for the id-matching caveat).

**Missing coverage:** 2xx body that parses to a dict but fails normalization (SAF-06); retry-loop re-permission (SAF-02); non-`SendRefusedError` failure inside T1 (SAF-01 B); `httpx.ConnectTimeout` classified `pre_connection` is only unit-tested for the exception type, not through a TLS-handshake timeout.

### Area 2: executor fencing, takeover, late completion

**Invariants checked and found sound**
- `acquire_execution` verifies the advisory lock in `pg_locks`, bumps the epoch in transaction A, commits, and only then reads attempts in transaction B (`operations.py:1472-1544`), so a late completion lands on one side of the epoch change; `_in_doubt` covers NULL, ambiguous, `exists_reported` and `accepted` attempts with no broker id, parks them UNKNOWN (`submission_failed -> unknown` is a legal transition, `transition.py:48`) and pauses `outcome_unresolved`.
- `authorize_send` and `complete`/`persist` writes serialize with takeover on the operation row (FOR UPDATE in T1, FOR SHARE in `fence_held`, `send_guard.py:50-69`); `cas_update_operation` fences on the updated row itself.
- `terminate_operation`/`end_operation` only move intents that are open, in an unsent state and `proven_not_sent`, bump the epoch and clear the executor in one locked step (`operations.py:1134-1198`, `:1266-1335`); End is refused while any Job of the operation is live; no broker call.
- `complete_attempt_late` is complete-once, requires the creating job id and epoch, never touches the order (`operations.py:1746-1840`).
- Lock keys: Start and Continue both lock `(strategy, as_of_session)` (`submit_orders.py:221`, `:1180`); the one-open-operation-per-strategy unique index (`0027`) serializes starts for different sessions.

**Missing coverage:** advisory-lock connection loss mid-run (fence is the only protection; no test drops the lock connection); unlock-failure path (SAF-12); concurrent End versus a committed T1 of a zombie executor (the epoch-bump versus NULL-attempt interleaving is argued, not tested with real threads).

### Area 3: Continue after a price pause

**Invariants checked and found sound**
- `check_intent_permission` precedence is fixed and the Continue-only `awaiting_reconciliation` step is present (`permission.py:452-545`); window `ELAPSED/SUPERSEDED` terminates before any pause; the in-run own Job does not count as a broker effect because `latest_broker_effect_at` uses Jobs with `completed_at` set (`latest.py:101-110`).
- `run_paper_continuation`: lock first, non-blocking; lazy expiry, then paused-to-running CAS or adoption of a crash-left running operation, then `acquire_execution`; an in-doubt intent pauses and sends nothing (`submit_orders.py:1141-1340`).
- Continue sends only unsent intents under the registered order; `create_new_version` is refused for continuation and by `VersionBypassRefusedError` (`submit_orders.py:2135-2181`, `:2220`).
- `pause -> price_moved_beyond_tolerance` sends nothing; no replanning or resizing in the check.

**Missing coverage:** identity assertion (SAF-03); kill switch/window during retries (SAF-02); window expiry between the permission check and the POST; a Continue whose operation was ended by expiry while a second Continue Job is queued.

### Area 4: recovery blocking across End, re-evaluation, new versions and ownership changes

**Invariants checked and found sound**
- End, expiry and re-evaluation never touch `PaperOrder`, attempt or recovery rows (`terminate_operation` writes only operation and intent dispositions); `resubmission_permitted` is constant False (`recovery.py:312-322`); a recorded statement is evidence only; there is no broker-cancel path.
- `create_new_version` refuses when any earlier version reached or may have reached the broker (`submit_orders.py:2135-2181`); `retry_existing` re-reads the attempt history in the registration transaction and parks UNKNOWN when it is not clean (`submit_orders.py:2255-2278`).
- A1 uses the effective state, so an unknown calendar keeps an operation open (fail closed); A5 is exactly the account-level predicate (`paper_account_checks.py:341-358`).
- Handover/release run all checks inside the singleton `FOR UPDATE` transaction (`operator_controls.py:604-653`).

**Missing coverage:** SAF-01 (operation-bound zero-attempt), SAF-04, SAF-05; KNOWN-1 shapes (legacy zero-attempt `pending_submission`, ambiguous-but-not-parked `submission_failed`).

### Area 5: ownership admission and handover concurrency

**Invariants checked and found sound**
- Lock order is singleton first everywhere: handover `FOR UPDATE` then strategy rows (`operator_controls.py:604-631`); admission `FOR SHARE` before the Job insert (`job_mutations.py:332`); retry takes the singleton before the original Job row (`job_mutations.py:504-523`); `_prepare_start` takes it `FOR SHARE` before creating the operation (`submit_orders.py:1702`). Session isolation is READ COMMITTED (no override in `db/session.py`), so the re-check after the lock sees the committed owner.
- Handover cannot interleave a running executor: A1 refuses while a broker-touching Job is queued/running or an operation is effectively open; the submit/handover race tests are present (`test_paper_ownership_controls.py:784`, `:829`).
- `load_trading_gate_state` reads kill switch, owner and subject in one statement (`operator_controls.py:427-509`).

**Missing coverage:** per-attempt re-check of owner/enabled/kill switch (SAF-02); handover while a paused operation's window has elapsed but is not yet persisted (A1 passes by design; no test for the follow-on lazy expiry after the owner changed back).

### Area 6: verified basis, partial fills, same-session allowance

**Invariants checked and found sound**
- TL-10 allowance key is (strategy, `intended_session_date`, symbol, side) over orders that reached or may have reached the broker, legacy orders included (`intent_identity.py:739-790`); a version bypass is refused; a rejected order consumes the allowance as specified.
- Partial fills: a partially filled order is a working order (`permission.py:207-262`) and pauses the operation; terminal-with-unfilled-remainder is never pursued (TL-11); fills are ingested idempotently by `broker_fill_id` and positions are derived from fills (`sync_orders.py:348-370`, `positions.py`).
- `verify_evaluation_basis` fails closed on a missing sync, an unapplied or non-terminal earlier order, a fill-quantity mismatch, a missing clean reconciliation inside the window, and a basis/fill-derived position mismatch (`intent_identity.py:262-340`); a sell that exceeds the position is caught at revalidation.

**Missing coverage:** SAF-08, SAF-09; KNOWN-2 consequence (`Position` rows missing after an account-path sync while fill-derived positions exist: basis verification fails closed with `basis_positions_mismatch`, but the per-intent revalidation reads `Position` rows only, so `duplicate_open_position` would not fire on a Continue); partial-fill sell leaving a remainder then a later-session exit.
