# Phase 20.1 Plan 02: Unambiguous Order Submission (COR-06) Summary

**An order POST is now a single logged attempt: every HTTP attempt is committed before and after in `order_submission_attempts`, retried only while the whole history is proven never-connected, and any ambiguous outcome parks the intent in UNKNOWN, fails the Job as outcome-uncertain and is never re-sent; duplicate-id replies trigger one verified lookup; the Alpaca status mapping is a closed table.**

## Accomplishments

- Migration `0023_phase20_1_order_submission_attempts` (down_revision `0022_phase20_1_active_paper_strategy`): PostgreSQL rejects an out-of-set outcome, a half-completed row (`(completed_at IS NULL) = (outcome_class IS NULL)`), a duplicate `(paper_order_id, attempt_number)` and `attempt_number < 1`. The six-value CHECK includes `deadline_expired` from day one (introspected from `pg_constraint` and compared with the StrEnum). Single alembic head.
- `services/execution/attempts.py`: closed `AttemptOutcomeClass` (six), `SubmissionClass` (five), `SubmissionIntentState` (six); pure `classify_attempt_exception`, `classify_http_response`, `classify_submission`, `derive_intent_state`; `DbSubmissionAttemptLog` (each method its own transaction, sequence spans sessions, complete-once via `SELECT ... FOR UPDATE` + `AttemptAlreadyCompletedError`, no delete or `started_at` update); `bind_attempt_log` / `current_attempt_log` ContextVar.
- `AlpacaClient.submit_order` is a dedicated loop: `_request_with_retry` is GET-only (POST raises `ValueError`); fails closed (`AttemptLogNotBoundError`, zero POSTs) without a bound log; refuses to send when the existing history is not clean; retries only while every attempt so far is pre_connection/deadline_expired and complete; ambiguous stops at once; 2xx with an unparseable body is ambiguous; 422 `client_order_id must be unique` does exactly one `get_order_by_client_order_id` and trusts the record only on a D-07 match.
- `get_order_by_client_order_id` returns `None` only for HTTP 404; 5xx/422/auth/transport errors raise (GET retries kept).
- `BrokerStatusClass` table over the 16 documented statuses plus legacy `held`: `done_for_day` working, `replaced` terminal_with_successor (new `ExecutionOrderStatus.REPLACED`), unmapped/missing -> unknown with `status_reason == "unmapped_broker_status"` (defaulted fields on `BrokerOrderSnapshot` and `OrderSubmissionResult`). `_sync_paper_orders` writes `status_class` / `status_reason` into the transition details.
- Submission loop: pre-send guard before the retry transition (any non-None/non-`not_sent` class -> zero sends, intent UNKNOWN via `BROKER_STATUS_UNKNOWN`, `submission_outcome_uncertain` ExecutionEvent with severity error / blocks_execution true, run stops with `AmbiguousOrderSubmissionError`); ambiguous -> UNKNOWN; `OrderRejectedError` -> REJECTED via `BROKER_REJECTED` (never retried); `OrderNotSentError`/others -> retryable `SUBMISSION_FAILED` as before.

## Plan adjustments / notes (no behaviour change to the spec)

- `deadline_expired` is stored, classified and counted as not-sent here; nothing in this plan ever writes it (20.1-15 does). `SubmissionAttemptLog` got one extra read, `intent_registered_at()`, for the D-07 check (the abstract `ExecutionService.submit_order` signature is untouched).
- Reconciliation matcher effect: `replaced` used to normalize to PENDING (expected local `submitted`); it now normalizes to `REPLACED`, which the matcher maps to its default expected status `unknown`, and sync moves the local order to UNKNOWN. This is the intended D-13 behaviour; no matcher code or test changed.
- The spec conflict recorded in the plan is implemented as stated: a 4xx-rejected intent ends in lifecycle `REJECTED` (not retryable `submission_failed`); derived intent state is still `rejected`.
