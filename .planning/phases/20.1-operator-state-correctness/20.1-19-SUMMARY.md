# Phase 20.1 Plan 19: Continue Job attribution and TL-4 terminal states Summary

**A Continue Job (payload `{mode: continue, operation_id}`) is now attributed to its operation's strategy by one shared SQL fragment used by every Job-strategy read, and the two TL-4 terminal states (flagged Job with a run and zero orders; legacy never-found order) are documented and proven blocking, visible via R3 and A5, with no release path.**

## Accomplishments

- `job_strategy_public_id_sql(alias)` (alias validated as a plain identifier): `coalesce(payload strategy_id, operation of payload operation_id (compared as text), newest execution_operation_jobs link)`.
- `_INTENTS_SQL` (flagged CTE column and the `:sid` filter), `_RECONCILIATION_SQL` (effect rows), `get_job_recovery` (resolved in the SAME first statement, statement count unchanged) and `latest_broker_effect_at` (ORM coalesce with the same precedence) use it. A flagged Continue Job of A no longer gates B or creates the account-level subject; a completed one no longer moves B's A6 boundary; a Job that died before its link row was written is still attributed.
- SAF-04: tested for a start Job and a Continue Job (its own paper_execution run, zero orders, zero attempts): stays `unresolved / execution_path_unproven` through two sync passes, an advanced clock and a later clean reconciliation; exactly one Job-level audit record appended and never an input; R3 lists `{intent_id null, unresolved, execution_path_unproven, blocking true}`; A5 refuses seeding, handover and release (409, `failed_checks == ["A5"]`); a control world without the Job passes.
- TL-4 legacy never-found order (flagged and unflagged origin Job): stays `not_found` / blocking / `resubmission_permitted` false through complete absence evidence, a `not_received` statement, a clean reconciliation and repeated syncs; R3 shows `evidence_package.complete` true. It resolves only when the broker shows it (found_verified + fresh clean reconciliation -> gate None, A5 passes). Zero POSTs and zero attempt rows throughout.
